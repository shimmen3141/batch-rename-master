# 手順書の前提(fixtureの用意)がエミュレータで実行できず、確認が最初の一歩で止まった

- 日付: 2026-08-25
- 観測: `013:T07` の manual 確認依頼。人間が着手して、準備の段で止まった
- 種類: 検証漏れ / 手戻り

## 何が起きたか

`013:T07` の [`manual-verification.md`](../specs/013-safe-android-rename/tasks/T07-implement-android-file-browser/manual-verification.md) は、確認の前提として「Download フォルダに捨ててよいファイルを3つ作る」を求め、方法を **「PC から転送しても、端末のファイルアプリで作ってもよい」** と書いていた。

人間がエミュレータで着手したところ、**エミュレータの Files アプリには新しいファイルを作る導線が無く**、手順1へ入れなかった。**確認したかった6つの手順は1つも実行されないまま止まった。**

同じ repository の先例(`005:T05` の manual、`docs/development/emulator-verification.md`)は、fixture を `adb push` する PowerShell を**そのまま貼れる形**で持っていた。`013:T07` はその形を踏襲していなかった。

## なぜ起きたか

**手順書の review が、手順書の「中身」しか見ていなかった。** この manual は独立review を2回通っており、attempt 1 の P2-4 と attempt 2 の P2-2 / P2-3 で**3回も修正されている**。ただし直したのはいずれも

- 現 revision では観測できない期待が書いてある
- そのとおり操作しても警告が出ない(拡張子・ルール永続化)
- 現 revision に無い UI 名が書いてある

という **「手順と実装・仕様の食い違い」** である。**「その手順を、人間が実際の検証環境で実行できるか」は、どの attempt でも問われなかった。** reviewer は container の中に居て emulator を持たないので、実行可能性は原理的に review 範囲の外側にある。

そしてこの前提は、**手順1〜6 のどれにも属さない「準備」**に置かれていた。期待も観測もぶら下がっていないため、「観測できない期待」を探す review の網に最初から掛からない。

もう一つの要因として、**書き方が選択肢の列挙になっていた。** 「PC から転送しても、端末のファイルアプリで作ってもよい」は、どちらか一方でも成立すれば正しく読める。Agent 側は「どれかで作れるだろう」で止まり、**どの環境でどれが実際に使えるかを確かめなかった。**

## 得られた知見

- **manual の「準備」は、手順本体と同じ強さで具体化する。** 前提が実行できなければ、その先の手順の正しさは1つも観測されない。**止まる場所としては最悪**である(全部が未確認のまま返ってくる)。
- **依頼する環境で使える手段を1つ名指しする。** 「A でも B でもよい」は、A も B も確かめていないときに書きやすい。**先例がある repository では、先例と同じ手段(ここでは `adb` + PowerShell)を既定にする。**
- **Files アプリを「用意する側」と「確かめる側」の両方から外す。** `adb push` したファイルは端末のメディア索引にすぐ載らないので、**実体と表示が食い違う**。アプリ側は索引ではなく filesystem を直接見るため影響を受けないが、人間が結果を見る窓としては不適切である。`adb shell ls -l` / `cat` を正とする。
- **独立review は「実行可能性」を保証しない。** reviewer は検証環境を持たない。**この確認は task 所有 Agent 側の責任**であり、依頼前に「人間が最初のコマンドから最後まで、手元の環境で実行できるか」を自分で辿る必要がある。

## ASDD側で緩和できること

- **`AGENTS.md` の manual 依頼の節へ、準備の実行可能性を加える。** 現在は「検証対象branch、exact commit/build、人間が実行する workspace を準備し、その状態を維持して待つ」と**対象側**の準備だけを求めている。**fixture・前提データの作り方が、依頼先の環境で実行できる形になっていること**は書かれていない。
- **`review-task` の skill が manual を見るときの観点へ、「前提が実行できるか」を明示する。** reviewer は実行できないので、**「実行手段が名指しされているか」「先例と同じ手段か」**という書式上の検査までは掛けられる。
- **`docs/development/emulator-verification.md` へ、fixture を置く定型 block を1つ置く。** 各 task の manual からはそこを参照し、task 固有のファイル名だけを書く形にすれば、task ごとに書き起こして抜ける余地が減る。
