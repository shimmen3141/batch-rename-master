# 契約・実装・testを同じtaskで書き、三者が同時にずれても気づけなかった

- 日付: 2026-08-21
- 観測: `013:T10` の独立review attempt 1(P1-1)
- 種類: 手戻り / ASDD手順の曖昧さ

## 何が起きたか

`013:T10` で、005 contract に新設した操作 **OP-005 `collectOccupiedNames`** の事後条件と、その実装と、その test が**三者とも食い違ったまま** review へ出した。

| どこ | 何と書いてあったか |
|---|---|
| 契約 OP-005 事後条件 | 「対象folder = **選択fileが属するfolderの集合**。そのすべてについて実在名を問い合わせる」 |
| 実装 | 対象folderを「**この実行で改名される**file(REQ-022の除外後)」に狭めていた |
| test | 「**改名される選択 file が1件も無ければ folder を問い合わせない**」を固定していた(契約と正面から反対) |

結果として実在した不具合: 同一folderに「生成後ベース名が空になる選択file」が2件以上あって強制実行すると、**自動解決がREQ-022の除外を解く**(2件目に ` (1)` が付いてベース名が空でなくなる)ので改名要求が増え、そのfolderの占有名が無いまま実行へ渡って `ArgumentError` が `execute()` の外へ抜けた。実行ボタンは fire-and-forget なので、**snackbar も dialog も出ず、改名も起きず、利用者からは何も起きない**。

`flutter test`(460件)も `flutter analyze` も mutation(42件すべて KILLED)も、**全部通っていた**。testが契約ではなく実装に合わせて書かれていたためである。

## なぜ気づかなかったか

**契約の条文・実装・testを、同じAgentが同じ流れで書いた。** 実装を書くときに頭にあったのは「除外されるfileは改名されないのだから、そのfolderは要らない」という一つの筋である。その筋のまま条文を読み返し、testを書いた。**三者が同じ誤解を共有しているので、相互チェックが成立しない。**

`013` の `plan.md` は方針として「**仕様を変えるものは、仕様更新taskと実装taskを分ける**」と書いている。**T10 はその方針から外れて定義されていた** — task の「変更範囲」に 001/004 の仕様改訂と 005 の実装が並んでおり、受け入れ証拠にも「契約をrevision 5へ更新し、人間の承認を得ている」が入っていた。方針は plan にあったのに、task がそれを守っていない。

もう一つの要因は **`autoResolve` が REQ-022 の除外を「解く」方向へ働く**という非自明な相互作用である。契約は「除外は自動解決の後に適用する」と書いており、除外の判定が自動解決の**結果**に依存することは読めば分かる。しかし実装時には「除外 → 改名されない」という一方向だけを見ていた。

## 何が救ったか

**独立reviewである。** reviewer は契約の条文を先に読み、実装がそれより狭いことを指摘した。さらに **testが契約と反対のことを固定している**ことまで見つけた。実装を書いた文脈から分離していなければ、この三者比較はできない。

mutation は救わなかった。**mutationは「実装が壊れたらtestが落ちるか」しか見ない。** 実装とtestが揃って契約からずれている場合、mutationは全件KILLEDになる。今回それが起きた。

## 得られた知見

- **契約を新設・改訂したtaskでは、「条文 → 実装」ではなく「条文 → test → 実装」の順で書く。** testを条文から直接起こせば、実装の都合が入る前に食い違いが出る。今回は実装を書いてからtestを書いたので、testが実装の写しになった。
- **mutationのPASSを「契約を満たしている」と読まない。** mutationが答えるのは「このtestは何かを検査しているか」であって、「正しいものを検査しているか」ではない。**契約との照合は別の作業である。**
- **「除外する」「対象外にする」系の判定は、その判定が後段で覆らないかを必ず問う。** REQ-022 の除外は自動解決の後に適用されるので、自動解決の出力次第で除外集合が変わる。**判定の入力が後段の出力に依存していないかを見る。**
- **独立reviewを「実装が正しいか」だけの工程と考えない。** 今回の価値は、**同じ人が書いた契約とtestと実装を突き合わせた**ことにあった。

## ASDD側で緩和できること

- **`AGENTS.md` の検証の節へ「契約を新設・改訂したtaskでは、testを実装ではなく条文から起こす」を加える。** 現在は「testの削除・skip・assertion緩和、errorの握りつぶしでPASSさせない」までで、**testが実装の写しになる**という型を扱っていない。
- **同じく「mutationのPASSは契約との一致を意味しない」を明記する。** 現在の記述は「testが本物かをmutationで確かめる」で止まっており、mutationが答えない問いが書かれていない。
- **planの方針「仕様更新taskと実装taskを分ける」を、task定義時の検査項目にする。** `013` はこの方針を持っていたのに、`T10` の定義がそれを破っていた。**方針をplanに書くだけでは、taskがそれを守るとは限らない。** create-plan / review-task のどちらかで「このtaskは仕様と実装の両方を含んでいないか」を問う。
  - 分けられない事情もある(T10 は、実装してみないと条文の妥当性が確かめられない性質があった)。**その場合は「条文 → test → 実装」の順と、独立reviewが条文と実装とtestの三者を突き合わせることを、taskの受け入れ証拠へ明示的に書く。**

## 改善結果

- 2026-08-21 / `f1f0628` で、対象folderを条文どおり「実体ハンドルを持つ選択fileすべて」へ広げた。契約 OP-005 の事後条件へ「**REQ-022で除外される選択fileのfolderも対象に含める** — 強制実行の自動解決は除外を解く方向へ働きうるから」を明記し、条文が理由まで持つようにした。
- 2026-08-21 / 契約と反対のことを固定していたtestを書き換え、回帰testを2件(unit / UI経路)追加した。UI経路では**結果の提示へ到達すること**を見て、例外が抜けて黙って終わっていないことを固定する。
- 2026-08-21 / mutation **M43**(対象folderをREQ-022の除外後へ狭める)を表へ足した。**この型の再発はmutationでも捕まるようになった** — ただしそれは「今回の具体形」に限る。
- 2026-08-21 / 独立review attempt 2 で PASS。reviewer は `targets` が `resultName` を見る前に登録されるため包含が `resultName` に依存しない形で成立することを構造で確認し、空ルール/handleなし/folder null/未選択のみのfolder/非強制経路も洗った。
- forward-test: **未実施。** 次に契約を改訂するtaskで、「条文 → test → 実装」の順が守られるかを見る。
