# 手動確認を旧buildで実行し、6手順すべてが無効になった

- 日付: 2026-08-25
- 観測: `013:T07` の manual 確認1回目。人間が最後まで実行し、全部が対象外のbuildに対する観測だった
- 種類: 検証漏れ / 手戻り

## 何が起きたか

`013:T07` は **Android のファイル選択の入口そのものを置き換える** task である(SAF の
システム画面 → app 内 browser)。人間が manual を最後まで実行して結果を返したが、
**端末に入っていたアプリは `dev`(`57c5e69`、T07 の前)のbuild**だった。

報告のすべてが旧buildの挙動と一致していた。

- 「すべて」で開いたのは **Android 標準のファイル選択画面**(ハンバーガーメニュー、
  サイドバー、パンくずリスト、`sdk_gphone…` という内部名、前回の場所の復元、
  複数選択に長押しが要る)。
- 手順3・手順4で **「SAF ではフォルダ内のファイル名を一覧できません(フォルダの権限が
  ありません)」**。これは `saf_file_source.dart:99` の文言で、`013:T10` が入れた
  **旧buildとしては正しい**停止である(005 REQ-027)。
- 手順5で注記が出ず、`data` も無い。app 内 browser の機能なので、旧buildには無い。

**このtaskについて確かめたかったことは、1つも観測されていない。**

## なぜ起きたか

**「ブランチが正しい」と「動いているbuildが正しい」を、同じことだと扱っていた。**

`docs/development/emulator-verification.md` には、2026-08-05 の同型事故(T3 のデモ用
フェイクを T4 の実装と誤認した)を受けた警告が既にある。しかしそれは **`git branch
--show-current` でブランチを確かめよ**という警告である。今回、**ブランチは最初から
正しかった** — host と container は作業ツリーを共有しており、Agent が branch を進めた
時点で host 側も同じ branch を指していた。**古いのは端末の中の APK だけ**で、branch の
確認では検出できない。

そして manual 側に、**アプリの画面から build を見分ける手がかりが1つも無かった。**
手順書は「先にこの branch の build を入れ」としか書いておらず、入っていなければどう
見えるかを書いていない。**入口の画面ごと置き換える task なので、見分けは本来いちばん
容易だった。**

さらに悪いことに、**旧buildは正しく動いていた**。「SAF では一覧できません」は
`013:T10` が仕様どおり出している停止であり、**エラーらしいエラーに見える**。人間からは
「新機能に不具合がある」と読め、「別のアプリを見ている」とは読めない。

## 得られた知見

- **manual の最初の手順は、対象buildが動いていることの確認にする。** ブランチではなく
  **アプリの画面から見分ける**。「こう見えたら新しい / こう見えたら古い」を両方書く。
- **UI が変わる task ほど、この確認は書きやすく、書き忘れやすい。** 見れば分かると
  思ってしまうが、**前の画面を知らない人間には分からない**。
- **「正しく動く旧build」は誤診を招く。** 旧buildが仕様どおりの停止メッセージを出す
  場合、人間には新buildの不具合と区別できない。**停止メッセージに含まれる語**
  (今回は `content://` と「SAF」)が、どのbuildの経路かを示す手がかりになる。
- **共有作業ツリーは branch 由来の事故を減らすが、build 由来の事故は減らさない。**
  むしろ「branch は合っているのだから正しいはず」という誤った安心を作る。

## ASDD側で緩和できること

- **`AGENTS.md` の manual 依頼の節へ、build identity の確認を加える。** 現在は Agent が
  「検証対象branch、exact commit/build、人間が実行するworkspaceを準備し、その状態を
  維持して待つ」ことを求めているが、**人間が手元で「今動いているのがそれか」を確かめる
  手段**までは求めていない。準備するのは Agent、確かめるのは人間で、後者の手順が要る。
- **`docs/development/emulator-verification.md` の警告を build へ広げる。** 現在の
  警告は branch の確認で閉じている。**「branch が正しくても端末のアプリは古い」**を
  同じ枠へ書く。
- **アプリへ build identity を出す**(version + short SHA を設定画面などに出す)。UI が
  変わらない task では画面から見分けられないため、この型の事故は再発しうる。**費用対
  効果の判断が要るので、`013` の plan 完了時に人間へ選択肢として出す。**

## 改善の反映

- 2026-08-25 / `013:T07` の manual へ **`## 0. いま動いているのが、このタスクのビルドか
  確かめる`** を足した。新旧の画面の見分け(タイトル、保存場所の一覧、チェックボックス
  の有無 / ハンバーガー、パンくず、内部名、長押し)と、`flutter run` までの手順、
  **旧buildだと手順3でどう見えるか**を書いた。
- **上の「ASDD側で緩和できること」3点は未着手。** `013` の plan 完了時に判断する。
