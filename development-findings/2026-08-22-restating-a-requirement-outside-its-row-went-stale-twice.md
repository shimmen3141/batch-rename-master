# 要求の範囲をREQ行の外へ書き写し、3回続けて古くなった

- 日付: 2026-08-22
- 観測: `013:T03` の独立review attempt 1(P1-1)、attempt 2(P1-A)、attempt 3(P1-1)
- 種類: 手戻り / ASDD手順の曖昧さ

## 何が起きたか

004 spec の REQ-018(`/Android/` 配下は改名できない可能性を示す)について、**同じ範囲の記述を spec の3箇所へ書き写していた**。

1. REQ 行そのもの(規範)
2. 「自由とする点」の項目 —「**`/Android/data/` 配下であることの示し方**(注記、アイコン、色)。REQ-018 は『改名できないことが分かる』までを定める」
3. 「013:T03 由来の更新」の Agent 決定表

attempt 1 で「REQ 行の範囲が一次資料より狭い」と指摘され、**1 だけを直した**。attempt 2 で「2 が古いまま」と指摘された。**2 は範囲(`/Android/data/` 限定)と強さ(「改名できない」と断定)の両方が、再承認された REQ 行と食い違っていた。**

しかも 2 は「自由とする点」に置かれていたため、**要求の上限を宣言する文**として読める。実装者は REQ 行と「自由とする点」の両方を読むので、「`/Android/data/` だけに断定文言で出す」実装が spec 全体を満たしてしまう状態だった。代表例も `/Android/data/` と `/Android/media/` しか無く、この narrow 実装を落とせなかった。

同じ型が REQ-015 でも起きていた(P2-1)。開発者の指摘で REQ 行を「保存場所の **root**」へ具体化したのに、Agent 決定表の「保存場所の**内側**」(指摘された当の判定不能語)がそのまま残っていた。

## なぜ起きたか

**読み手のために書いた要約が、規範のコピーになっていた。** 「自由とする点」も決定表も、本来は「実装に委ねる範囲」「なぜそう決めたか」を書く場所で、**要求の範囲を書く場所ではない**。しかし範囲に触れずに書くのが難しく、つい書き写した。

書き写した瞬間、**同じ事実の正本が2つになる**。片方を直しても、もう片方は静かに古くなる。構造検査も lint も test も、この不一致を検出しない(どちらも自然文である)。

`013:T10` で**同型を既に踏んでいた** — handoff の揮発値(CI run 番号、test 件数)が2回続けて陳腐化し、[別finding](2026-08-21-volatile-values-in-handoff-went-stale-twice.md)を書いた。そこで得た「**prose に揮発値を持たない**」は、**外部の揮発値**(CI run 番号)にしか適用していなかった。**同じ文書の中の規範を書き写すこと**も同じ問題だと気づいていなかった。

## 得られた知見

- **規範の範囲は、規範の場所にだけ書く。** 説明・自由・決定記録は「何を決めたか」を書き、「どこまでが対象か」は REQ を参照する。参照は古くならない。
- **「自由とする点」は特に危ない。** 実装の自由を書く場所だが、「REQ は〜までを定める」という形で**要求の上限を再宣言しやすい**。上限は REQ 行が持つべきである。
- **代表例が narrow 実装を落とせるかを確かめる。** REQ を広げたら、**広げた側の代表例を足す**。今回 `/Android/data/` と `/Android/media/` の例しか無く、`/Android/obb/` を足して初めて「`/Android/data/` 限定実装」が落ちるようになった。
- **同じ根本原因の2回目は、文言を直すのではなく複製をやめる。** `AGENTS.md` が定めているとおりだが、1回目の修正時に「他に書き写した場所は無いか」を探していれば2回目は起きなかった。**不適合を1箇所で見つけたら同じ表現を検索する**という既存の規約が、**自分が今書いた文書の中**には向いていなかった。
- **2回目の修正でも、その検索は不完全だった(3回目)。** 探したのは 004 spec の中だけで、**同じ commit で自分が新規追加した `T07` の表**へ届かなかった。「同じ表現を検索する」は、**変更した file だけでなく、その変更で新しく書いた file すべて**を対象にしなければ意味がない。**宣言だけでは実行されない** — grep の対象範囲を明示的に決める必要がある。

## ASDD側で緩和できること

- **`AGENTS.md` の正本の節へ「規範の範囲を規範の外へ書き写さない」を加える。** 現在は「同じ規約本文を別ファイルへ複製しない」「要約を複製しない」と**ファイル間**の複製を禁じているが、**同一ファイル内**の複製に触れていない。今回はどちらも 004 spec の中で起きた。
- **`define-behavior-spec` / `create-plan` の skill へ、「自由とする点」に要求の上限を書かない**を入れる。「実装に委ねること」だけを書き、境界は REQ を参照する。
- **REQ を広げる修正では、代表例も広げたかを確かめる**を review の観点に足す。「REQ は直ったが代表例が旧範囲のまま」は、**test のある feature なら test で落ちるが、spec だけの task では落ちない**。

## 改善結果

- 2026-08-22 / 「自由とする点」から REQ-018 の範囲と強さの再記述を**削除**し、「どこで示すか・何を意味するかは REQ-018 が定める。**ここへ書き写さない**」と理由付きで書いた。同じ注意書きを Agent 決定表(REQ-015 の分)にも入れた。
- 2026-08-22 / 代表例へ `/Android/obb/` を足し、`/Android/data/` 限定実装が代表例で落ちるようにした。
- 2026-08-22 / **上の「複製を消した」は不正確だった。independent review attempt 3 が3箇所目を見つけた** — `013:T07` の「仕様被覆」表の `REQ-018(`/Android/data/`は改名できない旨)` である。範囲と強さの両方が古く、しかも**この finding を書いた commit と同じ commit で新規追加した表**だった。「同じ表現を検索する」を宣言しながら、**その検索が自分が今書いた他 file へ届いていなかった。**
  - あわせて内訳の訂正: 本文が挙げた「3箇所」の3番目(Agent 決定表の REQ-018 記述)は attempt 1 の修正後は範囲として正しくなっていた。古かったのは REQ-015 側である。正しくは **REQ-018 が2箇所(「自由とする点」と `T07` 仕様被覆表)+ REQ-015 が1箇所(Agent 決定表)**。
  - さらに attempt 3 は、**「自由とする点」に REQ-015 の遡行上限の再記述が残っている**ことも指摘した(REQ-018 の同型記述を消した**2行上**である)。**適用が半分で止まっていた。**
- **3回続いたので、`AGENTS.md` の「同じtaskで独立reviewが合計3回FAILした」に従い `013:T03` を `blocked` にして人間へ返した。** 解き方の選択肢(現路線の改良 / 説明の全廃と機械検出 / 二重管理の対象を消す)を出している。**修正には着手していない。**
- 2026-08-22 / **開発者が「枠組みを変える」(案B)を選んだ。** prose の規律に依存するのをやめ、**書ける場所を機械が判定できる条件へ変えた。**
  - `tool/normative_terms.json` — 語ごとに **owner file** と **他 file での許可**を持つ。`allow` に挙がるのは「事実の出所」(research-matrix、ADR)と「日付つきの記録」(review の経緯)だけである。
  - `tool/check_normative_terms.py` — owner file では **REQ / INV / VER / OP 行と代表例の行にだけ**書けることを検査し、他 file では allow 以外を弾く。差し替えた古い言い回し(`保存場所の内側`)も `forbidden` として検出する。
  - **cross-task の「仕様被覆」表から括弧書きの説明を全廃し、REQ ID だけにした。** 説明が無ければ古くならない。
- 2026-08-22 / **検査を作った時点で、書き写しが5件見つかった。** independent review が挙げたのは2件(`T07` の仕様被覆表、`plan.md` の決定行)だったが、**指摘されていなかった2件**(004 spec 自身の更新要約と Agent 決定表)も出た。**prose を目で追う限り、3回の review でも全部は見つからなかった**ということである。
- 2026-08-22 / **検査が本物かを確かめた。** `T07` の表へ 3回目の指摘そのもの(`REQ-018(/Android/data/は改名できない旨)`)を注入すると **FAIL し、戻すと PASS する**。
- **残る提案(人間の作業)**: `AGENTS.md` へ「規範の範囲を規範の場所の外へ書き写さない」と、検証コマンドへ `check_normative_terms.py` を加えること。**規約の正本なので Agent は変更しない。**
- forward-test: **未実施。** 次に spec を改訂する task(`013:T07` が 004 と 005 contract を触る予定)で、検査が再発を止めるかを見る。
