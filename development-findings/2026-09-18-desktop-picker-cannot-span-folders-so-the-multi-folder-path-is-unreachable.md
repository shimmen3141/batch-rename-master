# desktopのpickerがfolderを跨げず、複数folderの状態がどこからも作れない

## 観測したこと(2026-09-18)

`008:T08` の手動確認の手順4(Windows desktop で2つのfolderから6件を選ぶ)で、開発者の報告は
**「そもそも別のフォルダのファイルを同時に選択することができませんでした。」**だった。
Windows のファイル選択画面は、1回の選択で1つのfolderの中しか複数選択できない。

これは 004 `spec.md` の前提と食い違う。

- **REQ-012**(親folderが跨る選択への警告)は「**Android では REQ-016 により選択が同一フォルダに
  限られるため発火しない。desktop では OS ピッカーが跨ぎを許すので引き続き有効である。**」と書いている。
- `013:T03` の REQ-016 で Android は常に1 folder になった。**残る跨ぎの経路は desktop だけ**だったが、
  その desktop でも(少なくとも Windows では)跨げない。

したがって現状、**複数folderが混ざった一覧はどちらのplatformからも作れない**。影響を受ける観測可能な
振る舞いは次の2つで、**どちらも到達不能な分岐**になっている。

- 004 REQ-012 の跨ぎ警告(`multi-folder-warning`)。
- 002 の代表例 7c(場所が2種類以上なら行に場所を表示する。`008:T22` で 2026-09-18 に再承認した)。

## なぜ気づかなかったか

- 004 の REQ-012 は 2026-08-20 に「desktop では引き続き有効」と**文章で**書き換えたが、
  **desktop の picker で実際に跨げるかを確かめていない**。Android 側(REQ-016)は実機で確かめている。
- `008:T08` は両方向を widget test で固定した。testは `FileListController` へ直接2 folderのentryを
  渡すので、**pickerの制約を通らない**。「機械で閉じた」と「利用者が到達できる」は別である。

## 変更先と検証

- **まだ仕様は変えていない。** 要否の判断は人間のものなので、`008:T08` の `task.md` へ観測として記録し、
  報告で出した。実装は**両方向を残したまま**である(到達不能でも誤りではなく、将来 macOS / Linux や
  複数回選択の蓄積で到達しうる)。
- 検証: `008:T08` の手順4は**実行不能**として記録した。手順書からは消していない
  (別のOSや将来の経路で実行できる可能性があるため)。
- 未確認: **macOS / Linux の picker が跨ぎを許すか。** 手元に環境が無く確かめられない。
  Windows でだけ跨げないのか、desktop 全体でそうなのかで、REQ-012 の扱いは変わる。
