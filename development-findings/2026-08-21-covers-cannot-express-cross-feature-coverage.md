# `covers`がcross-featureの仕様被覆を表現できず、埋めて戻す手戻りになった

- 日付: 2026-08-21
- 観測: `013:T10` の独立review attempt 1(P2-1)とその修正
- 種類: 仕組みの不足 / 手戻り

## 何が起きたか

`013:T10` は 001・004・005 の要求を実装する task である(013 自身の `spec.md` は権限と `renameat2` の話で、この task が触る要求を持たない)。independent reviewer が「`task.json` の `covers` が空である」を P2 として挙げたので埋めたところ、構造検査が15件の警告を出した。

```
WARNING: coverage reference 001:REQ-007 from 013:T10 is not present in /workspace/specs/013-safe-android-rename/spec.md
（以下14件同様）
```

`workspace.py` は `covers` の各IDを**所有planの `spec.md`** に対してだけ引く。`001:REQ-007` のような接頭辞付きの形も、素の `REQ-007` も、013 の `spec.md` には無いので未解決参照になる。**cross-featureの被覆を `covers` で表現する手段が無い。**

結局 `covers` は空へ戻し、被覆表を `task.md` の「仕様被覆」節へ書いた。埋める→警告→戻す→別の場所へ書く、という一往復の手戻りである。

## なぜ起きたか

**`AGENTS.md` が `covers` を「仕様被覆」の正本と書いているのに、その被覆先が所有planに閉じることを書いていない。** 検査の実装を読むまで分からない。

さらに `013` の `plan.md` は方針として「**`covers`は仕様task(T02/T03/T04)が埋める** … 各taskの受け入れ証拠に『対応する実装task(T05〜T08、T10)の`covers`を書く』ことを入れてある」と書いていた。**この方針自体が実現不可能だった** — T05〜T08・T10 が実装するのは他featureの要求だからである。方針を書いた時点では、`covers` が所有planに閉じることに気づいていなかった。

`013:T11`(done)の `covers` も空である。**前例はあったが、理由が書かれていなかった**ので、reviewer も実装Agentも「単なる未記入」と読んだ。

## 得られた知見

- **planを跨いで実装するtaskは、この repo の構造では珍しくない。** `013` は 001/004/005 を改訂して実装する plan であり、`006`(Windows D&D)や `010`(写真source)も同じ形になりうる。**`covers` が所有planに閉じる制約は、この構造と噛み合っていない。**
- **空欄には「空である理由」を書く。** 「未記入」と「表現できないので意図的に空」は外から区別できない。`013:T11` に理由が書かれていれば、今回の往復は起きなかった。
- **方針を書くときは、その方針が使う仕組みの制約を先に確かめる。** `plan.md` の `covers` 方針は、検査の挙動を確かめずに書かれていた。

## ASDD側で緩和できること

- **`AGENTS.md` へ「`covers` は所有planの `spec.md` のIDだけを指す」を明記する。** 現在の記述(`task.json`: task ID、status、依存、**仕様被覆**、Issue/PR番号、manual確認path)からは、他featureの要求を被覆に書けるように読める。
- **cross-featureの被覆を書く場所を決める。** 案は3つある。
  1. `task.md` に「仕様被覆」節を置く(今回採った形)。人間は読めるが機械検査は効かない。
  2. `covers` に `NNN:REQ-xxx` 形式を導入し、`workspace.py` が対象featureの `spec.md` / contract を引くようにする。**検査が効くようになるが、pluginの変更が要る。**
  3. 他featureを改訂するtaskは、そのfeature側にtaskを作る(`013:T10` ではなく `001:T07` として持つ)。**planの境界と作業の境界が合わなくなる**ので、今回の形とは相性が悪い。
- どれを採るにせよ、**「空の`covers`には理由を書く」**は独立に有効である。

## 改善結果

- 2026-08-21 / `013:T10` は案1を採った。`task.md` に「仕様被覆」節を置き、**`covers` を空にする理由も同じ節に書いた**(次のAgentが他featureのIDを入れて警告を出さないように)。
- 2026-08-21 / `013` の `plan.md` の `covers` 方針を、T10/T11 の実態へ合わせて更新した。
- forward-test: **未実施。** 次にplanを跨いで実装するtask(`013:T05`〜`T08` など)で、同じ往復が起きないかを見る。
