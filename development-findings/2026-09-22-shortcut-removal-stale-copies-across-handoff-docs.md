# Development finding: 近道の撤去で、引き渡し資料の写しが2回続けて古いまま残った

- 観測日: 2026-09-22
- 観測した作業: `008:T11`(app内file browserの入口と近道の提示を定義する)の独立review
- 改善先: ASDDの規約(正本を変えたときの写しの扱い)、`tool/check_normative_terms.py`
- 関連artifact: `specs/004-file-source/spec.md`のREQ-015、`specs/008-ui-alignment/tasks/T11-*/task.md`

## 観測した事実

004 REQ-015から「既知の場所への近道」の要求を外したところ、独立review(`gpt-5.6-luna`)が
**同じ型のFAILを2回続けて出した**。

- attempt 1 (`fbb19aa..82cbf4b`): `T12`の`manual-verification.md`、`T38`の`task.md`、`013:T03`の決定表に
  近道前提が残っていた。
- attempt 2 (`fbb19aa..43b3b65`): attempt 1 の3箇所は閉じたが、`T12`のmanualが**参照している**
  `013:T07`のmanual(手順0の見分けの目印、手順1の期待)と、`T39`の`task.md`、`T38`の別の行に
  同じ前提が残っていた。

**1回目の直し方(指摘された箇所を個別に直す)が、2回目のFAILをそのまま生んだ。**
AGENTS.mdの「同じ根本原因が修正後も2回続いたら解き方を変える」に該当する。

## なぜ起きたか

- 規範文(REQ)は1箇所だが、**それを前提にした記述は plan・task・manual・decisions へ広く散る**。
  特に**manualは「参照して使い回す」ため、参照元を直しても参照先が古いままだと現行でない期待が復活する**。
- 「done したtaskの記録」と「これから使う手順」が**同じ形(task.md / manual-verification.md)で置かれている**ため、
  書き換えてよいもの(現行の指示)と書き換えてはいけないもの(当時の証拠)の区別が読む側に委ねられている。
- `tool/check_normative_terms.py`は literal 一致しか見ないので、「近道」という語が**要求として**使われているのか
  **記録として**使われているのかを区別できない。

## その場の対処(解き方を変えた点)

指摘された箇所を追いかけるのをやめ、**`specs/`配下の全occurrenceを機械的に洗い出して3つに分類**した。

1. **現行の指示**(activeなtask・これから使うmanual) → 現行REQ-015へ更新する。
2. **当時の証拠**(doneしたtaskのmanual・記録) → **結果は書き換えず**、冒頭へ同一文面の注記を入れて
   「入口と近道の期待だけは現行でない。正本は004 REQ-015」と示す。
3. **無関係な語**(「全部空にする近道」など、機能としての近道ではない用法) → 触らない。

分類の全件は`008:T11`の`task.md`に表として残した。

## 改善案(このfindingの引き受け先)

- `product-map.md`の将来候補「**『写しが古くなる型』の仕組み化**」が既にこの型を持っている。
  **今回の観測を入力として足す** — 特に「**参照して使い回すmanualは、参照先の期待が変わると壊れる**」という経路は
  2026-09-02のfinding(`rationale-duplicated-into-four-places`)には無かった。
- 候補: 改訂したREQ IDを引数に、そのREQを前提にした記述を`specs/`から抽出して**注記の有無を必須にする**検査。
  literal一致ではなく「REQ IDまたはその要求語が、doneでないtask・manualに注記なしで現れる」ことを見る形。
- **着手判断の前にIssue化しない**(product-mapの方針のまま)。

## 追記(2026-09-22): 3回のFAILがすべて「記録と現実の一致」だった

attempt 3 はP2のみのFAILで、指摘は**`task.md`の「変更したfile」表が`git diff --name-only`の一意な一覧と
重複していた**ことだった(同じfileを2つのcommitで直したため)。attempt 1 のP2も同じ型である。

**3回のFAILのうち、仕様変更の中身(REQ-015の文面、代表例、自由とする点、Play審査riskの書き方)は一度も落ちていない。**
落ちたのは毎回、**正本の外にある写しと記録の網羅性**である。

改善案に次を足す。

- **gitから機械的に得られる情報(変更fileの一覧)を`task.md`へ手で書き写すことの是非**を問い直す。
  書き写す限り、commitを足すたびに古くなる。**表の代わりにrangeだけを書き、一覧はgitに委ねる**形が候補。
### もう一つの観測: reviewerの判定表記を規約へ照らさず採った

attempt 3 はP2だけの指摘だったが、reviewerは「FAIL」と書き、**実装Agentがそれをそのまま採って
`blocked`にした**。AGENTS.mdのFAIL基準は「成果物の欠陥のP0/P1が一つでもあること」なので、
**P2だけならFAILではない**。開発者の指摘で訂正した。

- **他のAgentの判定は、重大度と規約のFAIL基準へ照らしてから採る。** AGENTS.mdは「他のagentの結果を
  鵜呑みにしない」と書いているが、**実装側が見落としたのは指摘の中身ではなく判定そのもの**だった。
- 改善案: reviewを依頼するprompt側へ**FAIL基準(P0/P1)を明示**し、受け取った判定を採る前に
  「P0/P1が有るか」で確かめる手順を置く。

## 追記(2026-09-22): `008:T12`で、同じ型を「記録を書く手」で2回踏んだ

`T12`(実装)の独立reviewでも2回続けて同じ型が出た。**今度は写しではなく、`tool/check_normative_terms.py`が
禁じている literal を記録へ書いたこと**である。

- attempt 1: 手動確認の手順書へ、004 REQ-018が正本とする path を literal で書いた。
  full regressionに含まれる normative check が落ち、**`task.md`の「960 PASS」が現実と一致しなくなった。**
- attempt 2: **その指摘を`task.md`へ記録するときに、同じ literal をまた書いた。**
  「直した」と書いた本文が同じ規則を破っていた。

**検査自体は機能している** — literal 一致なので、書いた直後に`flutter test`を回せば必ず捕まる。
破れたのは検査ではなく**順序**で、「記録を書く → full regression を回し直す」をしていなかった。
`task.md`の検証結果表は**測った時点のcode/docに対する主張**なので、**記録を書き換えたら測り直す**。

改善案に次を足す。

- **検証結果表を更新するcommitでも full regression を回す**(「記録だけだから」で省かない)。
- `check_normative_terms.py`の対象に`development-findings/`と`task.md`が入っていることを、
  規約側の「記録の書き方」として一度書く。禁じられた literal を**引用するときの書き方**(REQ IDで参照する)が
  決まっていれば、同じ手戻りは起きない。
