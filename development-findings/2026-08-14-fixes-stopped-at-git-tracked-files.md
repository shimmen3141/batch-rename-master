# 修正がGit管理下のfileで止まり、PR本文へ伝播しなかった

- 日付: 2026-08-14
- 観測: `013:T02` review attempt 2 (P1-1)
- 種類: 手戻り / 検証漏れ

## 何が起きたか

attempt 1で「Play policyのinvalid usesを自分に有利に要約していた」と指摘され、`specs/`配下の5fileを直した。しかし**PR #137の本文には偏った要約が逐語で残っていた**。

- 「利用者が個々のfileを**手で選ぶだけの**file選択操作」— 原文に無い限定語。
- 「**残る不確実性は「審査に通るか」であって、「該当しうるか」ではなくなった。**」— attempt 1で否定された結論そのもの。
- `review base/head/range`も旧headのままで、reviewの同一性が追えなかった。

**開発者が配布riskを受容するかを判断する画面はPRである。** specs内が正しくても、PRを読んだ人間は誤った前提で承認する。今回のfinding群が「人間へ渡す判断材料が歪んでいたことが最も重い」と繰り返し書いていた当の欠陥が、**最も人目に触れる場所に残っていた**。

## なぜ起きたか

`grep`で訂正対象を全文横断する対処(2026-08-13の`review-fix-reached-only-some-files`)を入れていたが、**その`grep`はrepositoryのworking treeにしか届かない**。PR本文はGit管理下に無い。

つまり対処の適用範囲が「fileの集合」で定義されており、**「その主張が現れている場所の集合」で定義されていなかった**。同じ穴は次にもある。Issue本文、commit message、会話での報告。

## ASDD側で緩和できること

`AGENTS.md`はPR本文に含める項目(成果、実検査、review range、未解決P0/P1など)を定めているが、**「reviewの指摘を反映したらPR本文も更新する」を求めていない**。PRを「最初の検証可能なcheckpoint後にDraftを作る」と早期作成させる以上、**本文は必ず古くなる**。

- review attemptのたびにPR本文の`review base/head/range`と`未解決P0/P1`を更新することを、review記録の一部として明示する。
- 訂正の伝播確認を「fileをgrepする」ではなく「**その主張が載っている成果物を列挙して、全部を直す**」と定義する。成果物にはPR本文、Issue本文、人間への報告文を含む。

## 改善結果

- 2026-08-14 / PR #137の本文を中立な記述へ全面的に書き直し、range・未解決P0/P1・人間判断を現在の状態へ更新した。
- `T02/task.md`のreview記録へ、この根本原因を記載した。
- **forward-test**: 次のreview attemptで、reviewerがPR本文とspecs配下の記述の一致を確認できる状態になっているかを見る。
- 2026-08-14 / **forward-testは1回目でFAILした。** この改善結果を書いたcommit(`85fba32`)自身がheadを進めたのに、PR本文の`review base/head/range`を更新しなかった。attempt 3のP1-2として再検出された。
  - **足りなかったのは伝播先の列挙ではなく、再評価の契機である。** 「PR本文も伝播先に含める」と一度書いても、**成果物を変えるたびに見直さなければ**本文は即座に古くなる。とくに`review range`はcommitするたびに古くなる唯一の項目である。
  - 2026-08-14 / **2回目のFAIL。今度は向きが逆で、PR本文が契約より進んでいた**(attempt 3のP2-1)。派生成果物だけが修正済みになり、正本が取り残された。詳細は[2026-08-14-contract-edit-silently-discarded.md](2026-08-14-contract-edit-silently-discarded.md)。**「伝播先の集合」を管理する発想では両方向を覆えない** — 正本と派生を毎回突き合わせる必要がある。
  - 追加の緩和案: **review依頼の直前を単一の同期点にする。** 依頼するrangeを決めた時点でPR本文のhead/rangeと未解決P0/P1を書き換え、それ以外のタイミングでは触らない。「commitのたびに更新する」より守りやすい。
