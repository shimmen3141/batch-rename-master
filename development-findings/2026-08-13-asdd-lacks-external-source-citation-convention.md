# Development finding: 外部資料の引用規約がASDDに無く、2回目の再発時に打つ手も定義されていない

- 観測日: 2026-08-13
- 観測した作業: `013:T01`。独立reviewが3回連続FAILし、3回とも「加工したものを原文として提示した」ことが原因だった
- 改善先: ASDD plugin(`create-plan` / `define-behavior-spec` / `review-task` / `workspace.py`)、および`AGENTS.md`の再発規定
- 関連artifact: `specs/013-safe-android-rename/tasks/T01-decide-storage-boundary/research-matrix.md`、`decisions/ADR-002-...md`

## 観測した事実

`013:T01`は、Androidのstorage境界を**外部の公式資料**から判断するtaskだった。ASDDの他のtaskと違い、正しさの根拠がrepositoryの外にある。

独立reviewが3回FAILし、**3回とも同じ根本原因**だった。

| attempt | 何を原文として提示したか | 実際 |
|---|---|---|
| 1 | Playの許可条件 | WebFetchの**要約**を貼っていた。原文の「similar to / it's likely」が「only / permitted」に変わり、開いた例示が閉じたallowlistになっていた |
| 2 | `adb shell mount`の出力 | 人間の生報告を**整形**して貼っていた。判断材料になる`pass_through ... ext4`の行が落ちていた |
| 3 | `MANAGE_EXTERNAL_STORAGE`の付与範囲 | **逐語引用を直す作業の中で**、原文の`except`を`such as`と書いた。「書けない」が「書ける」に反転していた |

3回目は、**2回目の修正作業そのものが生んだ**誤りである。しかも反転の向きは、planを都合よく見せる方向だった。

人間の判断で、`research-matrix.md`と`ADR-002`から**引用ブロックを全廃**した。出典のURLと節名を示し、内容は自分の言葉で書き、「筆者の要約であって原文ではない」と明記する形へ変えた。

## ASDD側の問題(この件で見えたもの)

### 1. 外部資料をどう記録するかの規約が無い

`create-plan`も`define-behavior-spec`も、**根拠がrepositoryの外にある場合の書き方を定めていない。** ASDDが想定する正本はcode、test、spec、contract、decisionで、いずれもrepository内にある。

そのため筆者は`[一次]` / `[要spike]` / `[未到達]`という格付けを**自分で発明した**。発明自体は有効に働き(reviewerがその欄を検査できた)、`[未到達]`が「Play policyの原文を読めていない」を可視化した。しかし**発明された規約にはtoolingもreviewer checklistも無い**ので、格付けが破れても機械的には検出されない。

**提案**: ASDDへ「外部資料の扱い」を1節足す。最小案は次の3点。

- 外部資料は**転記しない**。URL、節名、取得日、そして自分の言葉での要約を書く。
- 主張が原文の一語に依存するとき(`except`か`such as`か、`only`か`likely`か)は、**その語が判断を分けることを本文へ書く**。
- 到達できない資料は`[未到達]`として明示し、それに依存する判断を保留にする。

### 2. `workspace.py check`が引用を検出できる

`specs/`配下(`history/`を除く)に`^>`で始まる行があり、近くに出典URLが無ければ警告する、という**安価なheuristic**が成立する。今回の3件はすべてこれで引っかかる。構造checkは既に全fileを走査しているので、追加コストは小さい。

### 3. `review-task`に「引用の原文照合」の工程が無い

3回のreviewで引用が照合されたのは、**筆者が依頼文で明示的に頼んだから**である。skillの手順には無い。外部資料を引用する成果物では、これは構造上必須の工程になる。

**提案**: `review-task`へ「外部資料の引用があれば原文と照合する。到達できなければBLOCKEDではなく『未照合』として報告する」を足す。attempt 3のreviewerはSAFの引用を照合できず、**その旨を正直に報告した**。この振る舞いは正しく、明文化する価値がある。

### 4. 「2回続いたら洗い直す」に、打つ手が定義されていない

`AGENTS.md`は定める。

> 同じ根本原因が修正後も2回続いたら類似修正を止めて仮定を洗い直す。

**この規定は2回目(attempt 2)で発火していた。** 筆者は発火を認識し、findingへ「人間の報告もtool出力も原文である」と書いた。**しかし行動は変えなかった。** 引用を貼るのをやめず、「今度は気をつけて貼る」を選んだ。結果が3回目である。

問題は「洗い直す」が**何をすることか定義されていない**点にある。記録することは洗い直しではない。今回、正しい行動は**構造的な変更**(転記をやめる)であり、それは3回目のFAILと人間の判断を経てようやく採られた。

**提案**: 2回目の発火時に、**修正の種類を変えることを要求する**。同じ手段での再修正を禁じ、次のいずれかを選ばせる。

- 手段を変える(今回なら「引用を持たない形にする」)。
- 検査を足す(照合工程を分離する)。
- 範囲を狭める(その主張を成果物から外す)。

そして**選んだ理由をtaskへ書く**。「気をつける」は選択肢に入れない。**注意力は手段ではない。**

### 5. 意図的な重複が伝播漏れを生む

ASDDは各文書の自己完結を求め、同じ内容がplan、task、ADR、matrixへ重複する。attempt 2のFAILは、attempt 1の修正が一部のfileにしか届かなかったことによる。これは設計の代償であって欠陥ではないが、**代償の存在をskillが警告していない**。

**提案**: `review-task`が指摘を出すときと、実装Agentが修正するときの両方へ「同じ主張が他のfileにも無いか検索する」を明記する。詳細は`2026-08-13-review-fix-reached-only-some-files.md`。

## 影響

- 独立reviewが3回分。`AGENTS.md`の3回FAIL規律に到達し、人間の判断を要した。
- 判断の結論(候補Eの採用)は変わらなかった。**壊れていたのは根拠の提示方法であって、根拠そのものではない。** SAFが使えない論拠とspikeの観測はreviewが3回とも無傷と確認している。

## 改善結果

projectでは引用ブロックを全廃し、出典+自分の言葉+「原文ではない」の明示へ移した。ASDD PR #10で外部証拠規律、review時の原文照合、主張の横断検索、同根原因2回後に修正の種類を変える規律を追加した。

Markdown引用のheuristic検査は、引用形式を使わない誤表示を検出できず、正当な引用への誤警告も生むため見送った。validatorへ意味判断を持ち込まず、実装Agentとreviewerが原文・取得経路を確認する。
