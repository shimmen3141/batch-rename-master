# 散文が主張した検査範囲がassertionより広く、独立reviewが4回続けて同じ形で落ちた

- 日付: 2026-09-01
- 観測: `008:T16` の独立review attempt 2 / 3 / 4 / 5。すべて**成果物の欠陥(記録)**としてFAIL
- 種類: 検証漏れ / 手戻り

## 何が起きたか

`008:T16` は独立reviewを6回受け、attempt 1〜3 は実装の欠陥、**attempt 2〜5 は同じ形の
記録の欠陥**でFAILした。実装は attempt 4 以降、reviewerのprobeで毎回裏が取れている。

4回とも形が同じである。**`task.md` や PR本文が「この範囲で検査している」と書き、
実際のassertionがその範囲を覆っていなかった。**

| attempt | 書いたこと | 実際 |
|---|---|---|
| 2 | 「通常のfont sizeで狭幅(320/360/411dp)の文言が切り詰められないことを`didExceedMaxLines`で検査している」 | 320/360dpでは件数labelだけを見ており、選択件数は411dp以上でしか見ていなかった。しかも事実でもなく、320dp・1000件で `1000 / 1…` になっていた |
| 3 | 「件数が増えても一覧の取り分が変わらない → N-9 がここで閉じる」 | 真なのは**file件数**に対する不変性だけ。N-9の主語は画面占有で、**原因の数 × 文字倍率**という別の変数で同じ占有が起きた。根拠のtestは`onEditRule`を渡しておらず、測っている構成に当のwidgetが**存在しなかった** |
| 4 | 「320〜731dp × `textScaler` 1.0/1.3/2.0 で、**いずれも**`onEditRule`を渡した製品経路で検査している」 | 320dpは占有testが使っておらず、file件数を測るtestは`onEditRule`を渡していなかった。**attempt 3 と同じ空振りを別のtestでもう一度作っていた** |
| 5 | 「警告が無ければ余白も出ない」(test名・コメント・`task.md`・PR本文の4か所) | assertionは`findsNothing`と**相対比較**だけ。呼び出し側が`Padding`で包み直すと両方が同じだけずれて通る。reviewerのmutationが実際にすり抜けた |

## なぜ起きたか

**「主張を書く場所」と「検査する場所」が別々にあり、人手で同期させていた。**

書くときは実装した内容を思い出しながら範囲を書く。検査は別のときに書く。両者がずれても
**testはPASSし続ける**ので、機械では気づけない。ずれに気づくのは、外から読む独立reviewerが
一文ずつ突き合わせたときだけである。

attempt 3 のあと「文を実態へ合わせる」で直したが、それは**ずれた瞬間を1回消しただけ**で、
同期の必要そのものは残った。attempt 4 で「文を直すのをやめ、主張が真になるよう検査の側を
広げる」へ変えたが、**狭幅にだけ適用して広幅に適用し漏れ**、5回目が出た。

根が同じである。**散文が独自に範囲を主張できる限り、書き手が2か所を正しく同期させ続ける
必要があり、それは失敗する。**

## どう直したか

`008:T16` の `task.md` に「占有の主張を散文で持たない」節を置き、次を規律とした。

- **占有・余白について、`task.md` と PR本文は範囲を主張しない。**
- 幅・文字倍率・件数・原因の本数は **testのparameter listだけが正本**とする。
- 散文は**test名を指すにとどめる**。

PR本文も「検査した範囲の正本は assertion であり、散文が独自に範囲を主張すると必ずずれる」と
明記し、幅と倍率の列挙を落とした。attempt 6 では**数値レベルでの再発は無く、PASSした**。

あわせて、この形を生む2つの技術的な罠も記録した。

- **`onEditRule`を渡さずにlayoutを測らない。** 渡さないと測りたいwidgetがtreeに存在せず、
  何を測っても通る。この空振りを2回作った。
- **切り詰めはoverflowを出さない。** `Flexible`+ellipsisは内容を切ることではみ出さないので、
  `RenderFlex overflow`を見る検査では原理的に落ちない。`didExceedMaxLines`で見る。

## 一般化できること

**「検査している」と書きたくなったら、書く代わりにtestを指す。** 範囲(幅、倍率、件数、
組合せ)を散文へ書き写した時点で、正本が2つになる。ASDDは「review rangeはPRのbase...head
diffを正本とし、本文へ書き写さない」と既に同型の規律を持っており、**検査範囲にも同じ規律が
要る**。

この一般化を `AGENTS.md` へ入れるかは人間の判断である。いまは `008:T16` の `task.md` に
task固有の規律として置いてある。

## 検証・forward-test

- `008:T16` 独立review attempt 6 = **PASS**。P0/P1 無し。記録の数値(261px / 41% / 25px /
  70px / 85.0 / 切り詰めの見え方)がreviewerのprobeで**すべて再現**された。
- 同 mutation M173〜M203 = **31件すべて KILLED, 0 SURVIVED, 0 SKIPPED**。
- forward-test = **失敗した**(2026-09-04、`008:T18` 独立review attempt 4)。**同じ形が5回目として
  出た。** `T18` の `task.md` が「補正が font size 比例であることで**機械側が押さえている**」
  「これで`manual-verification.md`の**すべての項目が成立した**」と書いたが、比例先の
  `rowWarningFontSize` はコンパイル時定数で利用者の文字倍率に追随せず、**実測では倍率 2.0 で
  自ら定義した上限を超えていた**(gap = 1.18 / 2.37 / 4.30 / 6.91px @ 1.0 / 1.3 / 2.0 / 3.0)。
  対象の manual項目(確認C)は**開発者の回答自体が無かった**。

  **`008:T16` で置いた規律が `008:T18` へ伝わっていなかった。** 規律は `T16` の `task.md` に
  **task固有**として置いたので、別taskの筆者は読まない。しかも `T18` が主張したのは
  「testが覆う範囲」ではなく**「manual項目を機械が代わりに閉じている」**で、
  `T16` の規律が名指ししていた形(幅・倍率・件数の列挙)に当てはまらなかった。
  **同じ根の別の面である** — 散文が独自に被覆を主張できる限り、対象がtestの範囲であれ
  manual項目であれ、正本が2つになる。

- 2026-09-04 の対処: `T18` の該当節から範囲の数値を落とし、**test名と mutation ID を指すだけ**に
  改めた。**「機械が押さえている」と書くときは、押さえている条件(既定の文字倍率だけ、など)を
  同じ文に書く**か、書けないなら残余riskとして引き受け先を書く。
  **規律をtask固有に置き続ける限り次のtaskへ伝わらない**ことが実測できたので、
  **置き場所の一般化は `specs/product-map.md` の将来候補**(`T17` の 2026-09-02 の決定で
  登録済みの「写しが古くなる型の仕組み化」)**と同じ枠で扱う。**
- 次の forward-test: **`008:T18` の独立review attempt 5**、および占有・layoutを主張する
  `008:T09` / `T10`。
