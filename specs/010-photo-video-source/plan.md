# 010 写真・動画の撮影日時と読み込み

## 目的

写真・動画の**撮影日時**を取れるようにし、「撮影日時の順に並べて連番を振る」「撮影日を名前に入れる」を、今の読み込み経路のまま使えるようにする。利用者から見ると次の状態になる。

- 写真・動画を読み込むと、撮影日時を持つファイルは作成日時の欄に撮影日時が入り、作成日時の順に並べられ、日時トークンで撮影日が名前に入る。
- 撮影日時を取れないファイルは、今と同じく「不明」として示され、警告が出る(名前を推測で埋めない)。

**アルバム・全件から選ぶ画面は、撮影日時の後に扱う**(下の「対象外」)。

## 出所

- `specs/product-map.md` の将来候補「010 写真・動画source」。
- 開発者が 2026-10-04 に始めると決めた。要求整理での決定は下の「人間の決定」。

## 境界

### 対象

- 004 REQ-010(作成日時を複数の経路で取る)のうち、次の2つの経路を実装する。
  1. **ファイルの中身**: 写真の EXIF `DateTimeOriginal`、動画に記録された撮影日時。端末に依らない(desktop でも取れる)。
  2. **Android の MediaStore の `DATE_TAKEN`**。根拠は [R-001](decisions/R-001-mediastore-date-taken-source.md)。
- 経路の順位、時刻帯の扱い、対象にするファイル形式、日時を見せるときの呼び名(「作成日時」のままか)を仕様にする(T01)。

### 対象外

- **アルバム・全件から選ぶ画面**(MediaStore の一覧。folder をまたぐ一覧になる)。撮影日時のあとに、このplanへtaskを足して扱う。
  そのときの入力: `008:T24` の申し送り(folder で束ねない。読み込み元の単位で開き直す入口を設ける。`specs/product-map.md` の 010 の行)。
- MediaStore の `DATE_ADDED`(MediaStore に入った日時)。コピーした日が入りうるので使わない(下の決定)。
- 更新日時での代替(既に採らないと決めている。001 INV-006)。
- 改名した後に MediaStore(ギャラリー)へ新しい名前を知らせること。改名そのものは今も path で行っており、010 で変わらない。要否はアルバムの画面を扱うときに確かめる。

## 方針

- 外部振る舞いの正本は 004 の `spec.md`(REQ-003 / REQ-010)のまま。このplanは `spec.md` を新設せず、**T01 が 004(と連動するなら 001・002)へ差分を入れて承認を得る**。product-map の前提「日時の意味変更は 001/002 を再承認する」に従い、001・002 の意味が動くかを T01 で確かめる。
- **中身から読む経路を先に置く**。`DATE_TAKEN` は中身の撮影日時から作られるが、時差を推定できないと空になり、時刻帯の表し方も違う(R-001)。中身から取れないときに `DATE_TAKEN` で補う、を既定の案として T01 で確かめる。
- 名前は元に戻しにくいので、**取れた日時の出所が「撮影日時」と言えないものは使わない**。推測値・代替値を返さない(004 REQ-003)。
- risk は strict とする: 誤った日時は名前に入って残り、後から区別できない。

## 全体の受け入れ条件

- [ ] EXIF に撮影日時を持つ写真・撮影日時を持つ動画を読み込むと、作成日時に撮影日時が入り、並び替えと日時トークンに使われる(Android と desktop)。
  - 証拠: unit test(fixture のファイルから読む。T02)、Android エミュレータの manual(T03)。
- [ ] 中身に撮影日時が無く、MediaStore が `DATE_TAKEN` を持つファイルでは、その値が入る(Android)。
  - 証拠: Kotlin と Dart の境界の test、Android エミュレータの manual(T03)。
- [ ] 撮影日時が取れないファイルは「不明」のままで、既存の警告が出る。
  - 証拠: unit / widget test(T02・T03)。
- [ ] 004(と連動する 001・002)の spec 差分を開発者が承認している。
  - 証拠: T01 の task.md の承認記録。

## 人間の決定

| 日付 | 論点 | 決定 | 決定者 |
|---|---|---|---|
| 2026-10-04 | 010 で最初に届けるもの | **撮影日時を先にする**(要求整理の案A)。アルバム・全件から選ぶ画面は後にする。今の選択画面から読んだファイルにも効くため | 開発者 |
| 2026-10-04 | 撮影日時として認める値 | **ファイルの中身の撮影日時と、MediaStore の `DATE_TAKEN`**(案B)。`DATE_ADDED` は使わない(コピーした日が入りうる)。開発者の条件「DATE_TAKEN も一般的に撮影日時として扱われるなら」は [R-001](decisions/R-001-mediastore-date-taken-source.md) で確かめた — scanner は中身の撮影日時からだけ入れる。登録する app が直接書く値は確かめていない | 開発者 |
| 2026-10-04 | ダウンロードしたファイル等にも日時を付けるために `DATE_ADDED` を使うか(開発者が再検討を求めた) | **使わない。撮影日時は上の決定のまま**(案A)。ダウンロードしたファイルには既存の**更新日時**(トークン・並び順)を使う — 多くはダウンロードした時刻である。`DATE_ADDED` を撮影日時の代わりに入れると撮影日か保存日かを後から区別できず、path での改名で MediaStore に登録し直されると改名した時刻に変わりうる(**未確認の推測**)。「追加日時」を別の日時として足す案(案B)は採らなかった。撮影日時が不明のときに更新日時のトークンを案内するかは T01 で扱う | 開発者 |
