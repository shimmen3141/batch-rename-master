## 目的（説明的・正誤判定には使わない）

メイン画面のプレゼンテーション状態層 `FileListController` の振る舞いを定義する。ファイル一覧の保持・選択・ソート・カスタム順・ルール注入から、各行の「現在名／変更後名（001 のプレビュー）」を供給する。ウィジェットはこの状態を描画する薄い層で、視覚デザインは本仕様の対象外（後日の参考デザインですり合わせ）。

## 境界

- 対象（in scope）: `FileListController` の状態と操作、**リストの置き換え/除去/全消去**（004 が供給、操作は本コントローラ）、行データ（RowView 列。**場所サブ情報を含む**）の算出、ソート種別、カスタム順への自動切替。
- 対象外（out of scope）: 実ファイルの**取得元・権限**（004）・リネーム実行（005）・ルール構築UI（003）・エクスプローラ D&D（006）・視覚デザイン（レイアウト/配色/余白）。リストへ供給する `FileEntry` の生成は 004（本コントローラは受け取った `FileEntry` を保持・操作するのみ）。
- アクター: ユーザー操作（ウィジェット経由）、注入元（003 の `RenameRule`、004 の `FileEntry` 一覧）。
- 入力: `List<FileEntry>`、`RenameRule`（注入、既定は元名トークンのみ）、`now`。
- 出力: 行データ列（各行の現在名・変更後名・選択状態）、現在のソート種別。
- 永続化される状態: なし（画面内の表示状態のみ）。
- 外部副作用: なし（ファイル操作は行わない）。

## 振る舞い

### 状態変数

- `items`: 表示順の `FileEntry` 列（`setFiles` で供給された順を初期表示順とする）。
- `selectedOf(item)`: 各 item の選択フラグ。
- `sortMode`: `name` / `createdAt` / `modifiedAt` / `size` / `custom`。**時系列は作成日時・更新日時の2種**を提供する（2026-08-04 開発者決定。旧「`createdAt` を `modifiedAt` へ置換」の方針を取り消し）。作成日時は取得できない場合があり（001 の `FileEntry`）、そのときの扱いは REQ-002 / REQ-011 が定める。
- `rule`: プレビューに用いる `RenameRule`（注入。既定は元名トークンのみ）。

### 操作（イベント）

| 操作 | 効果 |
|------|------|
| 初期化(files, rule) | `items` = 入力順、選択 = 全選択、`sortMode` = 入力順を表す `custom`、`rule` を保持 |
| `setSortMode(mode)` | `items` を mode の comparator で安定ソートし、`sortMode` を更新（`custom` 指定時は現在の順を保持） |
| `reorder(oldIndex,newIndex)` | `items` をその移動後の順に並べ替え、`sortMode` を `custom` へ自動切替 |
| `toggleSelection(item)` | その item の選択を反転 |
| `selectAll()` / `clearAll()` | 全 item を選択 / 全解除 |
| `setRule(rule)` | プレビューに使う `RenameRule` を差し替え |
| `setFiles(entries)` | 現在の `items` と選択を捨てて `entries` で**置き換え**、全件を選択状態にする。**蓄積しない**（004 REQ-004/005 由来。2026-08-05 に旧 `addFiles`（蓄積・重複排除・末尾追加）から変更） |
| `removeFile(handle)` | 元場所ハンドルが `handle` に一致する item を `items` と選択から除去する。一致が無ければ無変化（004 REQ-006 由来） |
| `clearFiles()` | `items` と選択を空にする（004 REQ-006 由来） |

## 決定済み事項（旧・未解決事項。2026-08-01 に確定）

参考デザイン（`docs/design/Bulk Renamer.html`）のレビューと開発者回答で確定。デザインは既定選択・ソート4種・自動カスタム順・ライブプレビューを追認した。

- 既定の選択状態: **全選択**（リネーム対象を明示しやすい。デザインの「12件を全選択した通常状態」と一致）。
- 名前ソートの順序: **自然順**（数値を数値として比較、`file2` < `file10`）・**大文字小文字を区別しない**。
- ソート方向: **昇順固定**（MVP）。昇降トグルは将来。
- 未チェック行の変更後名表示: **変更後名を供給せず現在名のみ**（プレビュー対象外を示す。REQ-007）。
- 同値時のソート安定性: **安定**（元の相対順を保持。REQ-002）。
- 初期 `sortMode`: **入力順を表す `custom`**（読み込んだ順をそのまま表示。開発者確定。デザインは初期を名前順で描いていたが、UI 側の初期表示は後続で名前順チップを既定選択にすれば整合するため、状態層の初期は入力順のままとする）。

### 004 T5 由来の更新（2026-08-04・開発者再承認済み）

開発者決定「作成日時ソートを残す」に伴う更新。実装は 004 T6。

- **時系列ソートは2種**: `createdAt`（作成日時）と `modifiedAt`（更新日時）を**両方**提供する（REQ-002）。2026-08-04 より前の「`createdAt` を `modifiedAt` へ置換する」方針は取り消し。
  - 理由: 画像ではリネーム順にとって撮影時刻が本質的である一方、更新日時は**このアプリのリネーム自体が書き換えてしまう**ため、時系列の基準として作成日時を失うと再リネーム時に順序が崩れる。
- **作成日時が不明な item の扱い（2026-08-04 開発者決定で改訂）**: 作成日時ソートの並べ替えキーを、不明な item については**更新日時で代替**する（REQ-002）。処理は失敗しない（REQ-012）。
  - 理由: 変更を加えていないファイルでは**作成日時と更新日時が一致することが多く**、末尾へ隔離するより有用な順序になる。当初案（不明は末尾・相対順保持）から変更。
  - **代替はソートキーの決定にのみ用いる**。`FileEntry` の作成日時を書き換えず、命名（001 の日時トークン）でも代替しない（001 INV-006）。名前は後から直せないため、命名と並べ替えでリスクが違う。
- **警告（REQ-011）**: 作成日時ソートが選択されているとき、**作成日時が不明な件数**と**更新日時で代替して並べている**ことを警告として供給する（0 件なら供給しない）。判定は**ファイル種別ではなく取得可否**で行う。
  - 理由: スクリーンショットのように「画像だが EXIF 撮影日時を持たない」ケースがあり、種別判定では誤って安心させる。取得可否で判定すれば、画像/非画像・EXIF 有無・将来の MediaStore 対応まで同一の規則で正しく動く。
- **行での識別（REQ-013）**: 各行が**作成日時（不明ならその旨）と更新日時の双方**、および**作成日時が不明か**を供給する。どの item が代替されたかを行レベルで見分けられるようにするため（開発者要望: 例「作成日時: 不明 / 更新日時: 2026/8/4 16:00」を強調表示、警告マーク）。**見た目（色・マーク）は視覚デザインとして非規範**で、実装は `AppColors` のセマンティック色を用いる。
- 依存: `FileEntry` の作成日時が「不明」を取りうる形になること（001 の用語 `FileEntry` / INV-006）。取得経路の追加（EXIF・MediaStore・NTFS 等）は 004 側の関心で、本仕様は変わらない。

### 004 T7 由来の更新（2026-08-05・開発者再承認済み）

004 の読み込み導線の再設計に伴う更新。実装は 004 T9。

- **`addFiles` → `setFiles`（置き換え）**（REQ-008）。複数フォルダの蓄積（作業セット方式）を取り消したため、読み込みのたびにリストを置き換える。
  - 理由: 実機検証で「複数フォルダにまたがる一括リネームは需要が薄い」と判断された（2026-08-05 開発者決定）。加えて、蓄積すると別フォルダの同名ファイルを 001 の重複検証が**実際には衝突しないのに重複と警告する**不整合があった。
- **「作成日時: 不明」の強調を作成日時ソート時のみに**（REQ-013）。他のソートでは表示はするが強調しない。
  - 理由: 004 は作成日時の取得経路を実装していないため実ファイルが全件不明になり、常時強調すると画面が警告色だらけになって意味を失う。
- **手動並び替えとカスタム順の提示条件**（REQ-014・2026-08-05 決定）: **連番トークンがあるときだけ**提示する。
  - 理由: 並び順が生成後名に影響するのは連番があるときだけで、それ以外では動かしても何も変わらない操作を見せることになる。ソートは「目的のファイルを探す・確認する」用途があるので常に提示する。
  - 補足（実装上の注意。T9 で扱う）: 初期 `sortMode` は `custom`（読み込み順）で、**これは操作表の「初期化(files, rule)」行と決定済み事項「初期 `sortMode`: 入力順を表す `custom`」が規範として固定**しているため変えない。連番が無い状態では「カスタム順」の選択肢を出さないので、**どのソート選択肢も選択表示にならない**。この見せ方（読み込み順であることをどう伝えるか）は視覚デザインの範囲で、状態層の初期値は変更しない。
