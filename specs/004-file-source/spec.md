# ファイル読み込み(file-source) 振る舞い仕様

- Status: draft <!-- draft → approved(人間が変更) → deprecated -->
- Level: Light（正しさの正本は本ファイル）

## 目的（説明的・正誤判定には使わない）

実ファイルの読み込み入口を定義する。抽象ポート `FileSource` が「フォルダを開く」「ファイルを選ぶ」の2経路で `FileEntry` 群を返し、UI 側はそれを**1回で差し替えず「作業セット(かご)」へ蓄積**する。フォルダ/ファイル選択を繰り返して**別フォルダのファイルも混在**でき、各ファイルは**元場所ハンドル(URI/パス)**で一意に識別される(005 のリネーム書き戻し先)。純粋部分(ポート契約・作業セットの蓄積/重複排除・002 への結線)はサンドボックスで検証し、実 SAF/実ピッカーはホスト検証(実装は 004 T4)。

## 境界

- 対象（in scope）: `FileSource` ポートの契約(`pickFolder` / `pickFiles`)、`FileEntry` の**元場所ハンドル**、**作業セット**の操作(追加 / 除去 / 全消去 / ハンドルによる重複排除 / 既定選択)、選択結果を 002 の `FileListController` へ供給する結線。
- 対象外（out of scope）: リネーム実行=実ファイル書き込み(005)。命名エンジン(001)・リスト/選択/ソート/プレビュー(002)・ルール構築(003)の既存振る舞い。**画像の撮影日時(不変キー)と「すべて/アルバム」横断ギャラリー**(MediaStore/EXIF ベース)は後続の専用機能。サブフォルダ再帰探索。ストレージ/権限の具体実装(SAF・OS ピッカー・使用プラグイン)は `FileSource` 契約を満たす限り自由(実装は T4)。
- アクター: ユーザー(フォルダ/ファイルの選択・除去操作)、`FileSource` 実装(プラットフォーム)、`FileListController`(作業セットの保持)。
- 入力: ユーザーの選択操作 → `FileSource` が返す `List<FileEntry>`(キャンセル=空)。
- 出力: 002 の作業セットに反映されたファイル群(表示順・選択状態・プレビュー)。
- 永続化される状態: なし(セッション内の作業セットのみ。権限 URI の永続保持は実装内の詳細)。
- 外部副作用: 読み取りのみ(フォルダ列挙・メタデータ取得・権限取得)。書き込みなし。

## 振る舞い

### 操作（`FileSource` ポート契約）

| 操作 | 契約 |
|------|------|
| `pickFolder()` | ユーザーにフォルダを選ばせ、そのフォルダ内ファイルを `List<FileEntry>` で返す。ユーザーがキャンセルしたら**空リスト**。各 `FileEntry` は元場所ハンドルを持つ。例外を投げない(REQ-008)。 |
| `pickFiles()` | ユーザーにファイルを個別選択させ(複数可)、`List<FileEntry>` で返す。キャンセルは**空リスト**。各 `FileEntry` は元場所ハンドルを持つ。例外を投げない(REQ-008)。 |

### 操作（作業セット = 002 コントローラの拡張）

| 操作 | 契約 |
|------|------|
| `addFiles(entries)` | `entries` のうち**ハンドルが既存にない**ものを、与えられた順で末尾に追加する。既存ハンドルと一致するものは無視(重複追加しない)。追加分は既定で選択状態。空リストは無変化(REQ-004/005)。 |
| `removeFile(handle)` | `handle` に一致するファイルを作業セットと選択から除去する。一致が無ければ無変化(REQ-006)。 |
| `clearFiles()` | 作業セットと選択を空にする(REQ-006)。 |

### 要件

| ID | 優先度 | 要件（外部から観測可能な文で） | 検証 |
|---|---|---|---|
| REQ-001 | must | `pickFolder()` / `pickFiles()` は `List<FileEntry>` を返し、ユーザーのキャンセルに対しては**空リスト**を返す。 | VER-001 |
| REQ-002 | must | 各 `FileEntry` は安定した**不透明な元場所ハンドル**(SAF URI / ファイルパス相当の文字列)に対応づく。2つのエントリはハンドルが等しいとき同一ファイルとみなす(重複排除と 005 の書き戻しの基準)。 | VER-001, VER-002 |
| REQ-003 | must | 各 `FileEntry` は `name`・`modifiedAt`・`size` を持つ。004 は `createdAt` の取得を保証しない(SAF で取得不能)。よって 004 の時系列の基準は `modifiedAt`(=「更新日時」)であり、「作成日時」としては提示しない。 | VER-001 |
| REQ-004 | must | `addFiles(entries)`: ハンドルが既存に無いものだけを与えられた順で末尾へ追加する。既存ハンドルと一致するものは追加しない(重複しない)。空リストの追加は無変化。 | VER-002, VER-003 |
| REQ-005 | must | `addFiles` で追加されたエントリは既定で選択状態になる。 | VER-002, VER-003 |
| REQ-006 | must | `removeFile(handle)` は一致エントリを作業セットと選択から除去し、`clearFiles()` は両方を空にする。一致が無ければ無変化。 | VER-002 |
| REQ-007 | must | 結線: `pickFolder`/`pickFiles` の結果を `addFiles` で作業セットへ反映すると、002 のリスト(表示順・件数)とプレビューに追加が現れる。キャンセル(空)では作業セットは変化しない。 | VER-003 |
| REQ-008 | should | `pickFolder`/`pickFiles` はアプリをクラッシュさせない。ユーザーキャンセルは空リスト。権限拒否・IO エラー時の返り値は本 Light 契約では**空リスト**とし(no-op・best-effort)、キャンセルとエラーの区別・エラー通知チャネルは後続で扱う([ASSUMED]、open_questions)。 | VER-001 |

### 代表例

| # | 入力/操作 | 期待 |
|---|---|---|
| 1 | fake `pickFiles()` が [a,b] を返す → `addFiles` | 作業セット=[a,b]、両方選択 |
| 2 | 続けて fake `pickFolder()` が [b,c] を返す(b は同ハンドル) → `addFiles` | 作業セット=[a,b,c](b は重複追加されない)、c は選択 |
| 3 | `pickFiles()` がキャンセル=[] → `addFiles([])` | 作業セット不変 |
| 4 | `removeFile(bのハンドル)` | 作業セット=[a,c]、選択から b も除去 |
| 5 | `clearFiles()` | 作業セット=[]、選択=空 |
| 6 | 別フォルダの [a,d](a と別ハンドル) を続けて追加 | 混在して蓄積(a,c,... の後ろに d)。同名でもハンドルが異なれば別ファイル |

## 波及: 001/002 の承認済み仕様の更新（実装前に人間の再承認が必要）

本機能は既存の承認済み仕様の外部振る舞いに触れる。004 T2 以降の着手前に、各仕様を更新し人間の再承認を得る(黙って変更しない):

- **002-file-list**: (a) `FileListController` に作業セット操作 `addFiles` / `removeFile` / `clearFiles`(本仕様 REQ-004〜006 準拠)を追加。(b) 時系列ソートのラベルを「作成日時」→「**更新日時**」に変更(REQ-003。`createdAt` を実データで保証できないため)。→ 002 spec.md の該当 REQ を更新 → 再承認。
- **001-rename-core(Strict)**: (a) `FileEntry` に**元場所ハンドル**を追加(REQ-002)。(b) 日時トークンの「作成(created)」基準の表記/扱い(撮影日時は後続機能で導入するため、004 段階では「更新」を中心に)。→ Strict のため 001 の契約更新 → `spec_lint --strict` → 人間の再承認。ハンドルの置き場(`FileEntry` フィールド / data 層ラッパ)は実装判断(004 T2)。

## 自由とする点（実装に委ねる）

- `FileSource` の具体実装(SAF / OS ピッカー / 使用プラグイン)とキャンセル検出の方法。契約(REQ-001/002/008)を満たせば自由。
- 元場所ハンドルの文字列形式(URI 文字列 / パス)と、`FileEntry` フィールドか data 層ラッパかの持たせ方(REQ-002 を満たせば自由)。
- 作業セットの内部データ構造・重複排除の実装(順序保持と REQ-004〜006 を満たせば自由)。
- 単一 `pickFolder`/`pickFiles` 呼び出しが返す**リスト内の並び順**は未定義(プラットフォーム依存)。作業セットは**追加された順**を保持する(表示順の初期値。以後の並び替え/ソートは 002 の責務)。
- 混在時のフォルダ名副題など UI 表示は 002/UI に委ねる(open_questions)。

## 対象外・未定義とする点

- 権限拒否・IO エラーの**詳細な通知**(トースト等)とキャンセルとの区別。本 Light 契約では空リスト(no-op)に丸め、区別は後続(open_questions)。
- 隠しファイル・システムファイルのフィルタリング方針([ASSUMED] フィルタせず、実装が返したものをそのまま扱う。open_questions)。
- 同時/並行の選択操作(単一ユーザー・単一プロセス前提)。
- 実ファイルの書き込み・リネーム(005)。撮影日時・横断ギャラリー(後続機能)。
