## 目的（説明的・正誤判定には使わない）

実ファイルの読み込み入口を定義する。利用者はまず**リネームしたいファイルの種類**を選び、種類に応じた選択 UI で**フォルダを辿ってファイルを複数選択**し、確定した集合がそのままリネーム対象のリストになる。抽象ポート `FileSource` がこの選択結果を `FileEntry` 群で返し、各ファイルは**元場所ハンドル(URI/パス)**で一意に識別される(005 のリネーム書き戻し先)。**選択は 1 回で完結し、蓄積しない**(2026-08-05 の決定。旧「作業セット(かご)方式」は取り消し)。純粋部分(ポート契約・置き換え・002 への結線)はサンドボックスで検証し、実 SAF/実ピッカーはホスト検証。

## 境界

- 対象（in scope）: **種類の選択**(どの選択 UI へ進むか)、**Android の app 内 file browser の振る舞い**(何を見せ、どこまで選べるか)、`FileSource` ポートの契約(`pickFiles` と結果型 `PickResult`=`Picked`/`Cancelled`/`Failed`、および `listNames` と結果型 `NameListResult`)、`FileEntry` の**元場所ハンドル**・**表示用の場所**・**所属 folder ハンドル**、**対象 folder の実在 entry 名の列挙**(005 が占有名を作る材料)、確定した選択集合で 002 のリストを**置き換える**結線、`Failed` 時のエラー通知。
- 対象外（out of scope）: リネーム実行=実ファイル書き込み(005)。命名エンジン(001)・リスト/選択/ソート/プレビュー(002)・ルール構築(003)の既存振る舞い。**画像の撮影日時(不変キー)と「すべて/アルバム」横断ギャラリー**(MediaStore/EXIF ベース)は後続の専用機能。サブフォルダ再帰探索。ストレージ/権限の具体実装(SAF・OS ピッカー・使用プラグイン)は `FileSource` 契約を満たす限り自由(実装は T4。**新導線の実装は T9**)。
- アクター: ユーザー(種類の選択・ファイルの選択)、`FileSource` 実装(プラットフォーム)、`FileListController`(リネーム対象リストの保持)。
- 入力: ユーザーの選択操作 → `FileSource` が返す `PickResult`(`Picked(entries)` / `Cancelled` / `Failed(error)`)。
- 出力: 002 のリストに反映されたファイル群(表示順・選択状態・場所サブ情報・プレビュー)、`Failed` 時のユーザー通知。
- 永続化される状態: なし(セッション内のリストのみ。権限 URI の永続保持は実装内の詳細)。
- 外部副作用: 読み取りのみ(フォルダ列挙・メタデータ取得・権限取得・**実在 entry 名の列挙**)。書き込みなし。

## 振る舞い

### 操作（`FileSource` ポート契約）

結果は3値の直和 `PickResult` で表す(不正な状態を型で排除する):

- `Picked(entries)`: 選択が確定した。`entries` は 0 件以上(空フォルダは空の `Picked`)。各 `FileEntry` は元場所ハンドルを持つ。
- `Cancelled`: ユーザーがピッカーを閉じ、何も選ばなかった(決定していない)。
- `Failed(error)`: 選択後のアクセス・列挙に失敗した。`error` は理由(`permissionDenied` / `io` / `unknown`)+任意メッセージ。

| 操作 | 契約 |
|------|------|
| `pickFiles()` | ユーザーに**フォルダを辿ってファイルを複数選択**させ、確定した集合を返す。結果を `Picked` / `Cancelled` / `Failed` のいずれかで返す。例外を投げない(REQ-001/008)。 |
| `listNames(folder)` | `folder`(所属 folder ハンドル)にある**実在 entry 名**を返す。結果を `NamesListed(names)` / `NameListFailed(error)` のいずれかで返す。例外を投げない(REQ-014)。 |

`listNames` の結果も2値の直和で表す:

- `NamesListed(names)`: 列挙できた。`names` は 0 件以上の名前の集合(空フォルダは空の `NamesListed`)。
- `NameListFailed(error)`: 権限・IO・フォルダ消失などで列挙できなかった。`error` は `PickError` と同じ理由(`permissionDenied` / `io` / `unknown`)+任意メッセージ。**「列挙できなかった」を「entry が無い」と混同できない**ようにするための直和である(005 REQ-027 がこの区別に依存する)。

`pickFolder()`(フォルダ単位のツリー権限で全件を読み込む経路)は**契約に含めない**(OQ-1 が解消し、システム画面の「Select all」で一括選択できることを実機で確認したため)。実装コードの削除は T9 で行う。

### 操作（002 コントローラ側）

| 操作 | 契約 |
|------|------|
| `setFiles(entries)` | 現在のリストと選択を**捨てて** `entries` で置き換える。全件が既定で選択状態(REQ-004/005)。**蓄積しない**(旧 `addFiles` のハンドル重複排除・末尾追加は取り消し)。 |
| `removeFile(handle)` | `handle` に一致するファイルをリストと選択から除去する。一致が無ければ無変化(REQ-006)。 |
| `clearFiles()` | リストと選択を空にする(REQ-006)。 |

## 自由とする点（実装に委ねる）

- `FileSource` の具体実装(SAF / OS ピッカー / 使用プラグイン)とキャンセル/エラー検出の方法。契約(REQ-001/002/008)を満たせば自由。`Cancelled` と `Failed` を実装がどう見分けるか(ピッカーの戻り値・例外の捕捉等)は自由。
- 元場所ハンドルの文字列形式(URI 文字列 / パス)・表示用の場所文字列の形(フルパス / フォルダ名)と、`FileEntry` フィールドか data 層ラッパかの持たせ方(REQ-002/009 を満たせば自由)。
- **所属 folder ハンドルの文字列形式と、同一性をどう成立させるか**(REQ-013)。デスクトップ実装は「シンボリックリンクを解決した絶対パス、解決に失敗したら正規化した絶対パス」を用いるが、**「同じ場所なら必ず等しい」を満たす限り手段は自由**。
- **`listNames` の列挙手段**(`Directory.list` / SAF / ネイティブ)と、結果をキャッシュするかどうか(REQ-014)。**取得のタイミングは 005 が決める**(005 REQ-028)。
- エラー通知の UI 表現(SnackBar / ダイアログ等)。REQ-008 の「リスト無変化のままユーザーに理由が伝わる」を満たせば自由。REQ-012(親フォルダ跨ぎ)の警告の見せ方も同様に自由。
- リスト置き換えの内部実装(順序保持と REQ-004〜006 を満たせば自由)。
- `pickFiles()` が返す**リスト内の並び順**は未定義(プラットフォーム依存)。002 は受け取った順を保持し、初期ソートは `custom`。以後の並び替え/ソートは 002 の責務。
- `Failed` の理由分類(`permissionDenied`/`io`/`unknown`)の内部判定基準は実装に委ねる(REQ-008 は「理由を通知する」までを規定)。

## 対象外・未定義とする点

- **`listNames` も隠し/システムファイルをフィルタしない**(決定 D-2 と同じ理由)。占有名は「その名前が使えるか」の判定材料なので、隠しファイルが名前を占めていることは**隠さず数える**。

## T5 由来の更新（2026-08-04・開発者再承認済み）

開発者決定「作成日時ソートを残す」に伴い、作成日時の扱いを更新した。実装は T6。

- **REQ-003 を更新**: 作成日時は**取得できたときだけ設定し、できなければ「不明」**とする（`modifiedAt` 等で代替して埋めない）。旧文「004 の時系列の基準は `modifiedAt` であり作成日時としては提示しない」は取り消し。
- **REQ-010 を追加**: 取得は**優先順位付きチェーン**（① コンテンツ由来: EXIF `DateTimeOriginal`・動画コンテナ・PDF・Office・XMP → ② プラットフォーム由来: MediaStore `DATE_TAKEN`/`DATE_ADDED`、Windows NTFS `CreationTime`）。どの経路を実装するかは自由で、**追加しても仕様は変わらない**（不明の件数が減るだけ）。
  - 補足（非規範）: SAF には作成日時の列が無い。`stat()` の `ctime` は inode 変更時刻であり作成時刻ではない。Windows の `CreationTime` は本物の作成時刻だが**コピーで更新される**ため撮影時刻とは限らない。
- 波及（実装前に人間の再承認が必要。T5 で更新済み）:
  - **001（Strict）**: `FileEntry` の作成日時が「不明」を取りうる／基準日時が取得不能なら日時トークンは空文字列（REQ-004）／`validate` が基準日時不明を警告（REQ-014）／不明を別の日時で代替しない（INV-006）。
  - **002（Light）**: 時系列ソートを**作成日時・更新日時の2種**に（REQ-002。**不明な item は更新日時をソートキーに代替**）／作成日時ソート時に**不明の件数と代替した旨を警告**（REQ-011）／不明を含んでも失敗しない（REQ-012）／各行が**両日時と不明フラグ**を供給（REQ-013）。
  - 代替は 002 の**並べ替えキーと表示に閉じる**。004 が返す作成日時は不明のまま（REQ-003）で、001 の命名でも代替しない（001 INV-006）。名前は後から直せないため、命名と並べ替えでリスクが異なる。

## 013:T03 由来の更新(2026-08-22 作成 / **2026-08-22 開発者再承認済み**)

Android のファイル選択を **SAF から app 内 file browser へ**作り直す。013 ADR-002 の「受け入れた条件2」による — `renameat2` は filesystem path を要り、SAF の URI は path へ変換できないため、候補 E を採ると Android の読み込み導線が変わる。

- **REQ-011 をプラットフォームで分けた。** Android は「画像」「動画」「すべて」の3つで、「文書」を出さない。
- **REQ-015 を追加**: app 内 file browser。保存場所の一覧 → 既知の場所への近道 → フォルダ階層。現在地を示し上位へ戻れるが、**辿れる上限は保存場所(共有ストレージのボリューム)の root** である。これは**権限が与える範囲そのもの**で、システム領域への到達経路を作らない。
- **REQ-016 を追加**: 選択は**同一フォルダ内に限る**。
- **REQ-017 を追加**: entry を**そのまま見せる**(絞り込まない)。
- **REQ-018 を追加**: 書き込めない領域を表示しているとき、改名できない可能性を示す。**隠さない。判定ではなく注記**とする(**対象範囲は REQ-018 が正本。ここへ書き写さない**)。
- **REQ-019 を追加**: 権限が無い間は browser を開かない。
- **REQ-012 を更新**: Android では REQ-016 により発火しない。
- **VER-005 を追加。**

### 人間の決定(2026-08-22)

| 論点 | 決定 |
|---|---|
| 複数フォルダを跨ぐ選択 | **同一フォルダ内に限る**(REQ-016)。004 plan の 2026-08-05 決定「一括リネームしたいのは同じフォルダ内の同種ファイルがほとんど」に素直で、占有名の列挙が1フォルダで済み、013 ADR-002 の「フォルダとファイルを管理する導線」にも合う。**代償: SAF の種類チップで事実上できていた跨ぎ選択ができなくなる** |
| `FileKind` の扱い | **Android では絞らない**(REQ-011 / REQ-017)。app 内 browser に MIME filter の手段が無く、拡張子リストを自前で持つと**リスト漏れでファイルが黙って消える**。決定 D-2 と同じ理由である |

### Agent が決めた点(承認の対象)

| 論点 | 決定と理由 |
|---|---|
| 何を見せるか | **保存場所 + 近道 + フォルダ階層のすべて**(REQ-015)。013 ADR-002 は「単なるファイル選択画面ではなく**フォルダとファイルを管理する導線**として作る」ことを Play の File management へ寄せる手段として挙げている。階層だけだと Downloads へ辿り着くのに手数がかかり、近道だけだとファイルマネージャに見えない |
| 隠し・system 領域 | **隠さない**(REQ-017、決定 D-2 を維持)。書き込めない領域は**注記する**(REQ-018)。ただし一次資料が「大半のサブディレクトリ」としか書いておらず境界が文書化されていないため、**判定ではなく注記**とし、最終的な可否は実行結果に委ねる。**選択も読み込みも妨げない** — 判定で機能を止めない。system 領域は **REQ-015 が定める遡行上限**によって到達経路を作らない(絞り込みで隠すのではない)。**対象範囲の定義は REQ-018 と REQ-015 が正本で、ここへ書き写さない** |
| desktop との差 | **仕様として認める。** desktop は OS ピッカーのまま、Android は app 内 browser。同じアプリで選択体験が2つになる。desktop 側を寄せる作業は行わない(対象外へ明記) |

### Play policy への寄せ方(013 ADR-002 の受け入れた条件1)

REQ-015 の「保存場所 → 近道 → 階層を辿り、現在地を示す」形は、permitted uses の **File management**(app 固有 storage 外のファイルとフォルダの access・編集・管理)へ寄せるための設計である。**ただし invalid uses の file selection activity を外れる保証は無い**(013 ADR-002 / 013 `spec.md` の未解決)。**提出物そのもの(store 説明文と `Permissions Declaration Form`)は人間の作業**であり、この spec の範囲外である。**ただし「このアプリの主目的をどう説明するか」は `013:T03` が決めた** — 草案と提出チェックリストは [`T03` の task.md](../013-safe-android-rename/tasks/T03-define-android-file-browsing/task.md) の「Play への提出材料」にある。

実装は `013:T07`。
