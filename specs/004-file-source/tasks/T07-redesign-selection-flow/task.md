- **残っている論点(spec の open_questions に落とし、承認前に解消する)**:
  1. **フォルダ内の一括選択ができるか**。システムのファイル選択画面(Android の DocumentsUI)に
     「すべて選択」に相当する手段があるかは**バージョン・メーカー依存**で保証がない。200 件のフォルダを
     まとめてリネームしたい場合に手選択しかないと実用に耐えない。案: (a) 種類「すべて」だけ**ツリー権限**に
     して全件読み込む(旧挙動を一部戻す)、(b) アプリ内に選択画面を作る、(c) 手選択のみで割り切る。
     ※「多めに拾ってリスト画面で外す」案は**却下済み**(そもそも多めに拾えない可能性がある / 選別は
     選択段階で行うのが自然で、リスト画面の役割は並び替えと確認に限る、という開発者判断)。
  2. **ドラッグでの手動並び替えの扱い**。出力に影響するのは**連番トークンがあるときだけ**(元名・自由テキスト・
     日時は並び順に依存しない)。一方でソート(名前順・日時順)は**閲覧・確認の用途で常に有意**。
     連番が無いときはドラッグハンドルを隠す/無効にするか、常時出したままにするかを決める(002 の振る舞い)。
  3. **親フォルダ同一の確認が要るか**。DocumentsUI はフォルダ移動で選択が解除されるため実質フォルダ跨ぎは
     起きないが、プロバイダ次第では起こりうる。跨いだ場合、001 の重複検証は最終名集合を全ファイル横断で
     数えるため**実際には衝突しないのに重複警告**が出る。案: (a) 選択の親フォルダが異なることを検出したら
     警告/拒否する安全弁、(b) 001 の重複判定を**フォルダ単位**に変更する(Strict 仕様の変更・再承認が要る)、
     (c) 実質起きないので何もしない。
  4. ~~**種類選択の粒度と名前**~~ → **2026-08-05 に解消**: 「**画像 / 動画 / 文書 / すべて**」の4つ。
     旧案の「フォルダ」は「フォルダを丸ごと選ぶ」と誤解されるため「**すべて**」に改名した
     (実態はファイルシステムを辿ってファイルを選ぶ)。詳細は spec の REQ-011。
  5. **画像経路の権限モデル**。MediaStore/フォトピッカーが返す URI は**読み取り専用**で、リネームには
     `MediaStore.createWriteRequest` の同意ダイアログが要る(Android 11+ は複数まとめて1回)。
     SAF のツリー/ドキュメント権限とは別物なので、写真機能側で改めて設計する。
- 参考: create-verifiable-spec skill、2026-08-05 の決定事項、T8 の結果(リネーム可否)、`docs/design/Bulk Renamer.html`
