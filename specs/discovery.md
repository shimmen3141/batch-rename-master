## 解く問題 / 対象利用者

スマホやPCで大量のファイル(写真・書類・ダウンロード物など)を、プレフィックス・サフィックス・連番・日時を組み合わせて一括リネームしたいユーザー。既存の手作業や汎用ツールは「リアルタイムに結果が見えない」「重複や桁あふれでファイル名が壊れる」「Android では全ファイルアクセス権限を要求され不安/審査リスク」といった不満がある。本アプリは **直感的なトークン組み立て + リアルタイムプレビュー + 実行前の安全検証(ドライラン)** で、安全で見通しの良い一括リネームを提供する。

- ターゲット: Android(主目標)、Windows。技術: Flutter。

## 機能候補

このアプリは以下の機能に分解できる(NNN は計画化時に確定。**コア命名エンジンを最初に計画する**)。

- **001 コア命名エンジン(最初に計画)** — 純粋 Dart 層。トークン列(元ファイル名 / 自由テキスト / 連番 / 日時)から新ファイル名を生成、リアルタイムプレビュー、ドライラン検証(重複検出・連番桁不足検出)、自動解決((1)(2) 付与・桁自動拡張)。UI とファイルIOを持たず、ファイルメタデータ(名前・作成/更新日時・サイズ)は**入力として受け取る**。データ整合性の核であり `flutter test` で完全に検証可能。→ **Strict 仕様候補**(実装・承認済み)。
  - 将来拡張(2026-08-01, 参考デザイン由来・保留): 「元のファイル名」トークンに**大文字化/小文字化(keep/upper/lower)**の変換モード。approved 済みの 001 Strict 仕様の外部振る舞いの追加に当たるため、着手時は 001 仕様更新 → `spec_lint --strict` → 人間の再承認 → 実装の順で扱う(現時点では 001 を変更しない)。
- **002 ファイル選択・リストUI** — メイン画面。現在名/変更後名の2カラム表示、チェックボックス選択、ソート(名前/作成日時/サイズ)、ドラッグでカスタム順へシームレス移行。001 のプレビュー結果を表示。
- **003 ルール構築UI(トークンビルダー)** — トークンの追加・並び替え(D&D)・詳細設定ダイアログ。モバイルはボトムシート、デスクトップは右側2ペイン。001 のルールモデルを編集する。
- **004 SAF フォルダ権限・ファイル読み込み(Android)** — OS標準ピッカーでフォルダURI権限取得、フォルダ内ファイルとメタデータの読み込み。`MANAGE_EXTERNAL_STORAGE` は使わない。**サンドボックスでは実機検証不可 → ホスト側の人間監督セッション**。
  - 追加要求(2026-08-01, 開発者): フォルダ全体だけでなく**対象ファイルを先に個別選択してからリネームへ進む**経路も持つ(ダウンロード等、目的ファイルが埋もれるケース対策)。フォルダ全体選択で従来のフォルダ一括挙動も再現できるため、上位互換の拡張。002 は `List<FileEntry>` を注入で受けるため影響なし(供給元の 004 で吸収)。計画化時に要求へ落とす。
- **005 リネーム実行(実ファイルIO)** — 検証通過後の一括リネーム、実行時バリデーション(警告時のキャンセル/強制実行ダイアログ)。**実ファイル書き込み → ホスト側検証**。
  - 追加要求(2026-08-01, 開発者/参考デザイン): リネーム実行後、一定時間だけ表示される**「元に戻す」トースト(セッション内・単一ステップ undo)**。実行直前のスナップショットを保持し、期限内なら元の名前へ戻す。永続履歴スタックは引き続き除外(スコープ境界参照)。計画化時に要求・検証へ落とす。
  - 追加要求(2026-08-02, 開発者): **リアルタイム警告表示(PRD §4.2)= 重複・桁不足の警告(001 `validate` 由来)を UI に出す**責務は 005 で扱う。002(ファイルリスト)では警告表示を持たない(002 spec の REQ 外)。005 計画化時に「プレビュー/実行前の警告ハイライト」を要求へ落とす。
- **006 Windows: エクスプローラーからの D&D 追加** — Windows 固有。エクスプローラーからファイルをリストへドロップして追加。**ホスト側検証**。

### 追加の機能候補(2026-08-02, 開発者要求。NNN は計画化時に確定)

003 のレビューで確定した、UI 構築(003)とは別の**永続化を伴う**機能。いずれも 001 の `RenameRule`/`Token` の**シリアライズ(JSON 等)を共有基盤**とし、ストレージ(Android/Windows で動く `shared_preferences` 等、テストは in-memory ポートで)を持つ。

- **(NNN) 前回ルールの復元** — 直近に組み立てた「現在のルール」1件を永続化し、次回アプリ起動時にそのルールから始める。003 の `RuleController` の初期値を保存値から復元し、変更時に保存する。失敗時は空ルールで開始(低リスク)。→ 003 完了後に `/create-plan`。
- **(NNN) ルールのプリセット保存/読み込み** — 名前付きルールを複数保存し、選んで適用する(参考デザインの「現在のルールを保存」)。上記の復元機能とシリアライズ基盤を共有。→ 別途 discover/plan。

### 大まかな機能間依存

- 002・003 は 001(命名エンジンのモデルとプレビューAPI)に依存。
- 004・005 は 002/003 の上で動く(実データを 001 に流す)。005 は 004 の権限取得が前提。
- 006 は 002 の追加経路の拡張。

## スコープ境界(アプリ全体)

- 作る: 上記 001〜006。まず 001 を計画・実装し、順に UI → プラットフォーム層へ広げる。
- 作らない(現時点): クラウド同期、**リネーム履歴の永続化(横断的な undo スタック・複数世代の巻き戻し)**、正規表現による置換、フォルダの再帰的探索(サブフォルダ横断)。※必要なら後続の機能候補として別途ディスカバリ。
  - 補足(2026-08-01, 参考デザイン反映): 上の除外は「永続的な履歴スタック」を指す。**直近リネームの単一ステップ undo(セッション内・時限トースト)は 005 のスコープに含める**(下記 005 参照)。両者は別物。

## 効いてくる制約

- **サンドボックス**: Android SDK / Xcode なし。`flutter run` / `flutter build apk` 不可。エージェント作業の検証は `flutter analyze` / `flutter test` / `dart format` が中心。**実機・プラットフォーム固有ビルドの確認はホスト側の人間監督セッション**(ビルドはホスト側で実施可能と確認済み)。→ 純粋 Dart のコア層を先に作る方針の根拠。
- **Android 権限方針**: `MANAGE_EXTERNAL_STORAGE` を要求せず、SAF のフォルダ単位 URI 権限を使う(Playストア審査リスク回避、実行時の逐一確認ダイアログ回避)。
- **データ整合性**: リネームはファイルを破壊しうる操作。重複・桁不足の検出と自動解決が中核要件 → 001 を Strict 仕様で。
- **レスポンシブ**: 画面幅でルール構築UIの表示方式を切替(モバイル=ボトムシート / デスクトップ=2ペイン)。

## 決定(要求レベル。create-plan の「決定事項」表へ引き継ぐ)

| 論点 | 決定 |
|------|------|
| 最初のスライス | コアロジック層(命名エンジン)を先に。UI/ファイルIOから分離した純粋 Dart 層。ビルド確認はホスト側 |
| コア機能の範囲 | PRD の4トークン全部 + ドライラン検証(重複・桁不足)+ 自動解決((1)(2)付与・桁拡張)をすべて 001 に含める |
| 001 のファイルIO | 持たない。ファイルメタデータ(名前・作成/更新日時・サイズ)は入力として受け取る |
| 001 の仕様レベル | Strict(データ整合性が核のため) |

## 残る主要な未決定事項(計画・仕様フェーズで詰める)

- 日時トークンの詳細: サポートするフォーマット記号の集合(`YYYY`/`MM`/`DD`/時分秒など)と、基準(作成/更新/現在)の扱い。→ 001 仕様の open_questions。
- 連番の詳細: 開始番号・桁数・増分・振り方の単位(選択順 vs 表示順)。→ 001 仕様。
- 重複自動解決の正確な規則: `(1)(2)` 付与の順序、既存ファイル名との衝突も見るか、拡張子の扱い。→ 001 仕様。
- ファイル名バリデーション: OS 別の禁止文字・最大長・空名の扱い(Android/Windows で差)。→ 001 仕様。
- 拡張子の扱い: 「元のファイル名」=拡張子除いたベース名(PRD明記)。拡張子は常に温存か、変更可能にするか。→ 001 仕様。
