# ADR-001: 純粋 Dart コアと重複検出スコープ

- Status: accepted
- Date: 2026-07-26
- Related requirements: REQ-005, REQ-007, REQ-010, REQ-012
- Related constraints: CON-001

## Context

命名エンジンはファイルを破壊しうる操作の中核であり、正しさを固定したい。一方、開発サンドボックスには Android SDK / Xcode がなく実機ビルドができないため、検証は `flutter test` / `flutter analyze` が中心になる。また Android と Windows で同一のリネームロジックを共有したい。加えて、リネーム後にフォルダ内の既存ファイルを上書きしないためのデータ整合性判断が必要。

## Decision

1. コアを `package:flutter` / `dart:io` に依存しない純粋 Dart 層(`lib/core/`)として実装する(CON-001)。ファイルメタデータと現在日時は入力として受け取り、ファイルシステムへはアクセスしない(INV-004)。
2. 重複検出の対象を「最終名集合」= 未選択ファイルの現在名 ∪ 選択ファイルの生成後名 とする。選択ファイルの生成後名がこの集合で2回以上出現するとき重複とみなす(REQ-007)。自動解決も同じ集合に対して衝突を解消する(REQ-010/012)。

## Why

- 純粋 Dart 化により、実機ビルドできないサンドボックスでも全ロジックを `flutter test` で完全検証でき、ASDD の内側ループ(テスト→修正)が回る。プラットフォーム層(004/005)からロジックを分離でき再利用性も上がる。
- 最終名集合ベースの重複判定は、リネームで未選択の既存ファイルを上書きする事故を防ぐ。同時に、選択ファイルが自分自身の旧名や「リネームで手放される旧名」を取るケースを誤検出しない(最終集合には旧名が残らないため)。

## Why not

- `dart:io` で直接ファイルを走査する案: テスト容易性とプラットフォーム分離を損なう。SAF 経由のアクセスは 004 の責務でもあり、コアに持ち込まない。
- 重複判定を「選択ファイルの生成後名同士のみ」に限る案: 未選択の既存ファイルを上書きするリスクが残る。データ整合性要件に反するため不採用。

## Consequences

- 得られるもの: サンドボックス内で完結する高いテスト可能性、プラットフォーム間のロジック共有、上書き事故の防止。
- 失うもの: 呼び出し側(004/005)がフォルダ内全ファイルのメタデータをエンジンへ渡す責務を負う(選択・未選択の双方)。
- 将来見直す条件: サブフォルダ横断や大量ファイルで最終名集合の構築コストが問題化した場合、集合構築の最適化を検討する。

## Verification

- CON-001 / INV-004: VER-005(determinism_test)でファイルシステム非依存・決定性を確認。
- REQ-007 / REQ-010 / REQ-012: VER-003(validation_test)・VER-004(auto_resolve_test)で未選択既存との衝突検出・自動解決後の一意性を確認。
