# VER 表を散文で書くと coverage が何も照合できない

- **症状**: `run_plan_helper.py coverage` が「VER-00n の成果物 '...' が存在しない」「VER-00n を担当するタスクが無い(覆う対象も未割当)」を全 Light 仕様で出した。原因は仕様側の書き方で、
  - **成果物パス**列に `` `test/spec_002_file_list/` 配下の**コントローラ unit テスト**（現在: `controller_test.dart`, ...）`` のような散文を書いていた。`_artifact_files()` はセルの中身を**そのままパスとして** `root / artifact` に渡すため、常に解決できない。
  - **対象**列に `REQ-001〜014` や `REQ-001/002/003(…説明…)` と書いていた。covers は `[,、/]` で分割して ID とみなすため、範囲記法は 1 個の未知トークンになり、スラッシュ記法は 2 個目以降が `002` になって ID として認識されない。
- **どこで**: create-verifiable-spec の spec.md(Light)テンプレートの検証表。0.4 の `coverage` が入るまで、この列は人間しか読まなかったため誰も気づかなかった。
- **その場の回避**: 成果物列を**素のパス**(ディレクトリ可)に、対象列を**カンマ区切りの完全な ID 列だけ**に正規化し、観点の説明は表の下の箇条書きへ移した。テスト側のコメントにあった `REQ-004/005` のような複合表記も、grep 照合を素通りするので `REQ-004/REQ-005` に展開した。
- **提案**: テンプレートの列見出しに「素のパス1つ」「ID をカンマ区切り(範囲記法・複合記法は不可)」と明記する。あるいは `spec_lint` を Light にも当てて、この2列を機械的に検証する。**verifier は以前この列に「ディレクトリ + 種別(現在: …)」と書くよう求めており**、人間の可読性を優先した指導が機械照合を壊す方向に働いた。両者が同じ形を要求するようにしたい。
