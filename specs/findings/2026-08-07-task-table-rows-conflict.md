# 並列タスクの PR が、必ずタスク表の行で衝突する

- **症状**: 005 の T2 と T3 を並列で走らせ、先に T2 の PR をマージしたところ、T3 の PR が `plan.md` でコンフリクトした。衝突箇所はタスク表の**隣接する2行**だけ:

  ```
  <<<<<<< HEAD          (T3 ブランチ)
  | T2 | … | pending |
  | T3 | … | done    |
  =======
  | T2 | … | done    |   (dev: T2 の PR がマージ済み)
  | T3 | … | pending |
  >>>>>>> origin/dev
  ```

  それぞれ**別のタスクの行**を変えているのに、行が隣接しているため git が1つの hunk にまとめてしまい、自動解決できない。

- **どこで**: run-plan の並列実行(1 worktree = 1 タスク = 1 ブランチ)。作業ログはタスクごとの `- ログ:` に分かれていて衝突しないよう設計されているが、**タスク表の状態列は1箇所に集まっている**ため、その配慮がタスク表には効いていない。

- **その場の回避**: 両方の `done` を採って手で解消した。機械的なので難しくはないが、**並列タスクの数だけ確実に発生する**(N 本並列なら後続 N-1 本が必ず衝突する)。

- **なぜ構造的か**: 状態は「1タスク1行」で表され、必ず隣接行に並ぶ。タスクが増えても行は近接したままなので、衝突確率は下がらない。ログを分離した理由(並列ブランチの追記どうしを衝突させない)が、状態には適用されていない。

- **提案**:
  - (a) **状態をタスク表から出し、タスク詳細の各節に `- 状態:` として置く**(ログと同じ分離)。表は生成物にして `index` 同様 CI で再生成する。筋は良いが書式変更を伴う。
  - (b) `.gitattributes` に `plan.md merge=union` を設定する。安価だが、同じ行の別バージョンが両方残るため状態列には使えない(行が二重化する)。
  - (c) 現状維持とし、**run-plan の手順に「並列時は後続ブランチで衝突するのが正常」と明記**して解消手順(両方の done を採る)を書く。少なくとも「何か壊れた」と誤解する時間は無くせる。
