# 書式変更が、CI へコピーしたスクリプトを黙って壊す

0.7 移行の直後、`ASDD sync issues` が**閉じていた Issue 34 件を reopen** した。移行手順の不足が引き金だが、**その手前にスイート側の構造的な弱点が2つ**ある。手順書に1行足すだけでは同じことがまた起きる。

## 起きたこと

`.github/scripts/` の3ファイルはプラグインからの**コピー**で、0.6 のままだった。0.7 でタスクの状態がタスク表からタスク詳細へ移ったため、旧パーサは表の `状態` 列を見て**全タスクの状態を空文字**と読んだ:

```
.github/scripts/run_plan_helper.py  → [('T1',''), ('T2',''), … ]
プラグイン 0.7.0 の同ファイル        → [('T1','done'), ('T2','done'), … ]
```

`project_plan_to_issues.py` は「done でない ⇒ open であるべき」と判断して reopen する。**`--no-close-done` は close を抑制するだけで reopen は止めない**ので、抑制設定は効かなかった。

## 弱点1: 旧パーサが「読めない」ではなく「空」を返す(fail-open)

これが本質。書式が変わったのに、旧パーサは**エラーを出さずに空文字を返し**、下流はそれを「未完了」という**意味のある値**として扱った。壊れたことが誰にも分からないまま、外部に見える副作用(Issue の一括 reopen)だけが起きた。

0.7 では計画の状態について「語彙外の値を approved 扱いしない(fail-closed)」が入ったが、**タスクの状態には同じ配慮が無い**。同種の事故は次の書式変更でも起こりうる。

**提案**: `plan.md` に**書式バージョンの印**を持たせる(例: ヘッダに `- 書式: 2`、または先頭の HTML コメント)。パーサは自分が知らないバージョンを見たら**読まずに異常終了**する。1行のコストで、「古いスクリプトが新しい成果物を誤読する」という事故の**全クラス**が消える。あわせて、タスクの状態が語彙(`pending`/`in_progress`/`done`/`blocked`)に一致しない場合は例外にする(空文字を「未完了」と解釈しない)。

## 弱点2: コピーであることが、どこにも記録されていない

`.github/scripts/*.py` はプラグインの複製だが、**どのバージョンの複製かがファイルにもリポジトリにも書かれていない**。ずれても検出できず、比較するにはプラグインの実体パスを知っている必要がある。

**提案**: どちらかで足りる。

- (a) コピーの先頭に由来を書く(`# copied from asdd-suite 0.7.0 skills/run-plan/scripts/`)。`asdd_config.py check` がプラグインの現在値と突き合わせて警告する
- (b) そもそもコピーをやめる。CI で `pip install` 相当か、リリース済みのアーカイブを取得する形にすれば複製が消える

## 弱点3(手順書): 0.7 の移行手順にコピー更新が無い

0.5 の手順書には「`.github/scripts/` にコピーが必要」という注記があったが、0.7 には引き継がれていない。**書式変更を伴うリリースでは再コピーが必須**なので、手順に明記したい。ただしこれは弱点1・2があるから致命傷になるだけで、**手順書だけ直しても再発する**(人間もエージェントも手順を落とす)。

## 併発した別の問題

同じ実行の `Write back issue numbers into plan.md` も失敗した(`failed to push some refs`)。同時刻に走った `ASDD index` の push と競合したと見られる。結果として **plan.md の `issue` 列は空のまま**で、誤って reopen された Issue をタスクに突き合わせるのにタイトル照合が必要になった。生成物を統合ブランチへ書き戻すワークフローが2本あり、互いに競合しうる構造になっている(リトライか直列化が要る)。
