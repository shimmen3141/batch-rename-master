# T21 連番の桁数と桁不足の扱いを定義する

## 目的

連番の桁数を、**実際につく名前と警告が食い違わない**形にする。仕様を決めて人間の承認を得る
ところまでで、実装は承認後に別taskへ切る。

## 観測の出所

`008:T20` の実機確認(2026-09-16)で開発者が挙げた。原文は
[`T20` の task.md](../T20-rule-and-exec-bar/task.md) の「あわせて受領した指摘」にある。要点:

- 9件・連番1桁・開始10 → 名前は正常に `10`〜`18` になるのに、行に「連番の桁不足」が出て混乱する。
- 案A: 桁数をファイル数から決まる桁より小さくできなくする(100件なら2桁以下は選べない)。
- 案B: ゼロ埋めする / しないを選べるようにする。

**案A・案Bとも「〜べきだと思った」「一つの方法」という書き方で、どちらに決めたかは未定である。**

## 衝突する正本

- **001 の桁不足の判定**(`specs/001-rename-core/spec.md`「連番の計算値が `10^桁数` 以上」、
  REQ-008、自動解決 REQ-011)。開始10・1桁は計算値が常に `10^1` 以上なので、**全件が同じ幅でも警告になる。**
  001 spec に「なぜ桁不足を警告するか」は書かれていない — **着手時に理由を確かめること**
  (候補は「ゼロ埋めで揃えた幅が崩れ、名前順で並べたときに順序が狂う」)。
- **003 spec「決定済み事項」の連番の入力範囲**(`digits ≥ 1`)。案Aは件数に依存する下限を足す。
  エディタは件数を知らない(003 は 002 と独立)ので、どこで制約するかが論点になる。
- 案Bは 001 の `SequenceToken` に意味を足す。**001 は Strict contract なので、意味変更には人間の承認が要る。**

## 決めること

> **2026-09-17 の開発者決定**: ゼロ埋めなしの選択肢は `T05`(token追加の確定手順)に含めず、このtaskの案Bとして
> 決める。経緯は [`T05` の task.md](../T05-define-token-add-modal/task.md) の「人間の決定」。


1. 桁不足を警告する**理由**。理由によっては「全件が同じ幅なら警告しない」(案C)が案A・Bより小さい変更になる。
2. 案A / 案B / 案C のどれを採るか(組み合わせを含む)。**「そもそも変えない(文言だけ直す)」も選択肢に入れる。**
3. 001 の判定が動く場合、`008/plan.md` の方針(「判定・契約が動くときは別planを立てる」)に従い、
   **このtaskを 001 側の新しいplanへ移すか**。
4. 案Aの場合、件数が変わったとき(読み込み直し・選択の変更)に、既に設定済みの桁数をどう扱うか。

## 調査(2026-09-29)

着手は Claude Opus 5.5。branch `asdd/008-ui-alignment/T21-define-sequence-digits`、起点`dev`@`88b712e`。

- **桁不足を警告する理由は、どの正本にも書かれていない。** 001の`spec.md`・`plan.md`・`decisions/ADR-001`・task(T05/T06)・`history/`を検索した。書かれているのは判定(「連番の計算値が`10^桁数`以上」、`lib/core/rename_engine.dart`の`validate`は選択件数での最大値の桁数 > `digits`)と自動拡張(REQ-011)だけ。
- 出どころはPRD(`docs/proposals/001-PRD.md`。正本ではない): 連番は「開始番号、桁数(**ゼロ埋め**)」、警告は「連番の桁数が不足している箇所」、例は「2桁指定で100番目」。**ゼロ埋めで揃えた幅が崩れる**(`99`と`100`で幅が違い、名前順で並べると`100`が`11`より前に来る)ことを防ぐ警告と読める。
- 観測の例(9件・1桁・開始10)は`10`〜`18`で**全件が同じ幅**。上の理由に当てはまらないのに、判定が「指定桁数を超えるか」なので警告になる。
- 判定を動かすと、002 REQ-015(行の対象の導出: 「指定桁数を超えて描かれる item」)と005の代表例20c・20c′の文言も連動する。008 planの方針(判定・契約が動くときは別plan)により、判定を変える案なら001側の新しいplanへ移す。
