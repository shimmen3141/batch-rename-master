# T19 警告の詳細modalを作り直す

## 目的

`T17`で承認された仕様どおり、警告の詳細を**行スコープと全件スコープ**に分け、同じ説明が
ファイルごとに繰り返される形をやめる。

## 入力と依存

- **`T17`で承認された 002 / 005 spec。承認前に着手しない**(`plan.md`の方針)。
- 現行実装: `lib/ui/file_list/rename_warning_view.dart`(`describeWarning`、詳細dialog、
  `presentWarnings`)。
- `T18`が決める「行のどこを押すと開くか」。**入れ物はこのtaskが持つ。**

## 変更範囲

観測の出所は[`T16`のtask.md](../T16-implement-row-level-warnings/task.md)の
「受領したUIの改善要望(2026-09-02、原文)」。番号は同節のもの。

- **要望2(スコープ)**: 行から開いたときは**その行の警告だけ**、ヘッダの件数から開いたときは
  全件。`T17`が承認した形に従う。
- **要望3(重複)**: 「『ルールの問題』と『桁不足1件』の2セクションで重複して桁不足に
  触れられている」。要望7で桁不足が行の警告になるため、セクションの持ち方ごと組み直す。
- **要望4(長さと冗長さ)**: 「警告モーダルが縦に長すぎる。また、表現が冗長。モーダル内で
  ファイルの場所を括弧内に示す必要はない。説明も同じ内容がファイルごとに列挙されて見づらいので、
  同種の警告ならそのセクションの一番最初に『以下のファイルは作成日時不明です。作成日時トークンは
  空になります。』と書き、その下に該当ファイルを列挙するのが良さそう。」
- **要望5(文言)**: 「基準日時なし」をやめ、**「作成日時不明」「更新日時不明」**と基準を
  明示する。種別を並べるときは**「・」で区切る**。桁不足は**「連番の桁不足」**とする。
  `_locationSuffix`(ファイル名の後ろの場所)を落とす。

  **`T18` が行のラベルだけ先に揃えた**(2026-09-02)。いま **行は `作成日時不明` /
  `連番の桁不足`、詳細modal(`describeWarning`)は `基準日時なし` / `桁不足`** という
  不一致が残っている。**利用者から見て同じものが2つの語彙で呼ばれる状態なので、
  このtaskが揃えること。** ルール設定button側は `T20` が引き受ける。

### `T14`との分担

`T14`は**実行前確認dialog**(`file_list_view.dart`の`Key('rename-confirmation-dialog')`)を
持つ。このtaskが持つのは**警告の詳細**である。**同じmodalに二つのtaskが手を入れない。**
`describeWarning`系の文面は実行前確認dialogも使っているので、**着手時にどちらが文面の
正本を持つかを決めて両方の`task.md`へ書くこと**(`T16`が`T14`と同じ約束をしている)。

## 引き受けた残余risk(`008:T16`から)

- **R-A SURVIVED**: `presentWarnings`で基準日時不明を**fileごと1件へ畳んでも**743件すべて
  PASSのまま通る。**件数と詳細の数え方((file × 日時トークン)ごとに1件)を固定する
  assertionが無い。** 2026-09-02の独立review attempt 7 が挙げ、3条件を満たさないため
  受容してこのtaskへ送った。開発者が確認を求めた「82件」(27件 × 日時トークン3本 + 桁不足1)の
  数え方そのものである。**このtaskが数え方を決め直し、決めた数え方を固定するassertionを置くこと。**

- **「導線の無い`FileListView`単体では原因の説明を出さない」方向の assertion が消えた。**

  作り直すときに縮む方向を縛ること。**3条件の判定と受容の根拠は
