## 目的

2026-09-02のemulator確認で開発者が挙げた**警告の再設計**を、002 / 005 specの要求として
定義し、**人間の再承認を得る**。実装は`T18`(行)、`T19`(詳細modal)、`T20`(下部バー)が行う。

**これは仕様変更である。** 開発者の要望のうち3点が、2026-08-29に承認済みの正本と衝突する。
Agentが自分で緩めてはならない(`AGENTS.md`)。

`spec.md` は代表例を担う。**契約の REQ-009 そのものとは衝突しない** —
(1) は「対象ファイルを持たない警告(連番の桁不足)は**この限りではない**」と桁不足を
**許容**しており禁止していない。(3) は「全件と、各警告の説明を読める提示を用意する」だけで
**経路の数を課していない**。硬い衝突は **002 spec 側**(REQ-015・例19)と **005 spec の

## 決めること

### 1. 警告をファイル単位へ一本化する(要望6・7)

開発者の原文: 「そもそも同じような内容の警告をルール設定ボタンや各行・モーダルに重複して
書くことが混乱のもとになっているように感じた。警告は基本的にルールを変える方向に働くはずなので、
ルールにわざわざ書く必要が無い気もしてきた。現状だと警告が散らばっていてどこを見ればよいのか
分からなくなってしまっている。」「連番も、桁数をオーバーしたものに対して個々に表示したい。
ルールの警告は無くす。これによって、ルールの警告と個々のファイルへの警告の2つに分かれて
いたものが、個々のファイルへの警告だけになって認知負荷が下がると思う。」

**衝突する正本**:

- **005 spec の代表例20c**: 「連番の桁が足りないルール → 桁不足を提示する。**対象ファイルを
  持たないので、ファイルごとの提示にはならない**」。要望7はこれを真逆にする。
- **002 REQ-015**: 「**ルール全体に対する警告(連番の桁不足)は行データに含めない** —
  001の`DigitShortageWarning`は対象ファイルを持たず、特定の行に帰属しないため」。
  桁不足を行へ出すには、行データが桁不足を受け取れる必要がある。

**決めること**: 001の`DigitShortageWarning`は対象fileを持たないまま、**提示側が
「桁があふれる行」を特定できるか**。連番の値は表示順で決まるので、桁数を超える行は
一意に決まる(例: 桁1・開始100で27件なら、100〜126すべてが1桁を超える)。
**判定は001のまま変えない**(`plan.md`の方針)ので、**行への割り当ては提示側の派生**として
定義することになる。派生の規則を002へ書くか、005の提示要求として書くかを決める。

### 2. 行からの詳細は、その行だけを見せる(要望2)

開発者の原文: 「ヘッダーの警告のモーダルは全表示だが、各行の警告ではその行の警告だけを
表示することを私は想定していた(ユーザは各行で起こっている問題を把握したいはず)。」

**衝突する正本**: **005 spec の代表例20e**: 「全件の提示を、ファイルごとの警告からも一覧全体の
件数表示からも開く → **同じ内容**が読める」。要望2はこれを分ける。

**決めること**: REQ-009 (3)(全件と説明へ到達できる)を、**ヘッダの件数からの経路だけで
満たす**形にしてよいか。行からの経路がその行だけを見せるなら、全件への到達手段は
ヘッダだけになる。**「到達できる」の起点を1つに絞ってよいか**が論点である。

### 3. 変更が生じないときの提示と、実行の可否(要望1)

開発者の原文: 「ルールが空なら、『.jpg』のような変更後名を各列に出さず、『(変更なし)』の
ような表示を出したい。色は青などで強調しない(参考designもこうなっている)。また、ルールに
元の名前だけを設定したときも同様の表示にしたい。なお、ルールに元の名前だけを設定したときに
リネームボタンを押せるようにするかは考える余地がありそう。参考designではルール未設定時と
同様に押せないようになっている。」

**触れる正本**:

- **002 REQ-006**: 「行データは現在の`items`順で供給され、**選択行の変更後名は001の
  `generatePreview`に一致する**」。空ルールの`generatePreview`は`.jpg`のような拡張子だけの
  名前を返すので、`(変更なし)`はこれと一致しない。**データの供給を変えるのか、提示だけを
  変えるのか**を決める。
- **005 REQ-019**: 「**ルールが空のとき**、実行は開始されない」。要望1は「元の名前だけの
  ルール」でも押せなくする案で、**空でないルールに対する新しい実行不可条件**になる。

**実行buttonの文言(要望14)はこのtaskの対象ではない** — 文言は「自由とする点」に残っており、
`T20`が持つ。ここで決めるのは**押せるかどうか**だけである。

**着手した最初の質問として、この実行可否を人間へ確認する**(`AGENTS.md`「一度に一つ、
現実的で相互排他的な選択肢」)。参考designは`execLabel: !sel.length ? '対象を選択して
ください' : changeCount ? changeCount + ' 件をリネーム' : 'ルールを設定してください'`で、
**変更が0件なら押せない**側である。

### 実行可否の決定(2026-09-02、開発者)

提示した3案は **(a) 変更が0件なら押せない(参考design準拠) / (b) 押せるままで結果の出し方を直す /
(c) 元名のみのルールという形で特別扱いする** で、開発者は **(a) を選んだ**。

**判定はルールの形ではなく結果で行う。** `[元の名前]`1つだけのルールも、同じ結果になる別の形の
ルールも同じ扱いになる。(c) を採らなかったのは、`[元の名前]` + 空になった固定文字のような
同値の形を拾えず判定が脆くなるためである。

**着手して分かったこと**: 「変更後名 ≠ 現在名」だけで数えると**空のルールが「変更あり」に化ける**。
空のルールの`generatePreview`は拡張子だけの名前(`.jpg`)を返し、現在名と異なるからである。
そこで用語「**変更が生じるファイル**」を契約へ足し、**空のルールでは0件と定める**ことで、
REQ-019 を条件1本にまとめた。

**現行実装の事実**(判断の前提として確認した): 生成後名が現在名と同じ改名は、既に
`RenameStepKind.unchanged` として**ポートを呼ばずに成功記録**される(`rename_execution.dart:184`)。
つまり現状でも実体は壊れないが、**「N 件をリネームしました」と出る**。(a) はこの偽の成功表示も消す。

### 契約(`behavior-contract.json`)を動かしたか

**動かした。ただし REQ-009 は変えていない。**

| 変えたもの | 理由 |
|---|---|
| 用語「変更が生じるファイル」を追加 | REQ-019 の条件を1本にまとめるため。空のルールを0件と定める |
| **REQ-019** を「ルールが空のとき」→「**変更が生じるファイルが0件のとき**」へ | 開発者の決定(a)。実行可否は契約の要求なので、契約を動かさずには表せない |
| **REQ-029** を追加(変更が生じないことが読める) | `(変更なし)`の要望。空のルールの拡張子だけの名前を変更後名として出す実装を排除する |
| **SM-001** の`requestExecute` guard 3本を同じ条件へ揃え、0件で止まる遷移を1本追加 | 要求と状態機械が食い違うと、宙に浮いた遷移が残る(`005:T8`で verifier が同じ型を指摘している) |

**当初は「REQ-009 は変えていない」と判断したが、独立review attempt 1 がこれを覆した。**

(1) が桁不足を「**この限りではない**」と**免除している**こと、(3) が**経路の本数を課していない**ことは
正しい。だが**それは「出してよい」の向きにしか成り立たない。** 開発者の要望7(桁不足を個々のファイルへ)
と要望2(行からはその行だけ)を**義務づける must が、どこにも無かった** —

- 005 REQ-009 (1) は桁不足を**免除している**ので、行に出さなくても違反しない。
- 002 REQ-015 が課すのは**行データが持つこと**だけで、同 REQ 自身が「提示方法は 005 が定め」と書く。
- 005 spec の代表例は、同ファイル冒頭が「**正しさの正本は contracts/behavior-contract.json**、
  **正誤判定は契約が行う**」(Level: Strict)と宣言している。

つまり「行データは桁不足を持つが、どこにも個別には出さない」実装が**すべての must を満たして**
しまう。`T18`/`T19`の`covers`が`005:REQ-009`を指しているのに、指した先が免除していた。
**REQ-009 を次の2点で変えた。**

| 変えたところ | 内容 |
|---|---|
| (1) の免除条項 | 「対象ファイルを持たない警告(連番の桁不足)はこの限りではない」→ **「連番の桁不足も、その連番が指定桁数を超えて描かれるファイルについては同じように種別が読める」**(対象の導出は 002 REQ-015)。001 が返していないときはどのファイルも当たらない |
| **(4)** を追加 | **ファイルごとの警告からはそのファイルの警告を読め、全件は絞られない入口から読める。範囲が混ざらない** — ファイルごとの入口が全件を出す実装も、全件の入口が1ファイルに絞られる実装も排除する |

**場所・文言・UI部品には踏み込んでいない。** 課しているのは**範囲**であって配置ではないので、
revision 8.0 が引いた境界(`T15`が3回FAILした線)を越えていない。

### 波及して直したもの(このtaskが見つけた)

**代表例21 が新しい REQ-019 と衝突していた。** 例21は「例20(作成日時トークンだけのルールで
全件が空名)の状態で強制実行 → 除外した件数と理由が出る」だったが、**全件が除外に当たるなら
変更が生じるファイルは0件**なので、新しい REQ-019 では強制実行の経路へ入らない。
例21を「**そのファイル以外に変更が生じるファイルがある**まま強制実行」へ狭め、全件除外の場合を
例21a として分けた。**利用者から読めなくなる情報は無い** — 除外の理由は REQ-009 の提示から読める。

**この例21aの説明が、最初は事実に反していた(独立review attempt 1 の P1-2)。** 「8.0 までは実行へ
入って**全件が除外**されていた」と書いたが、実際は違う。**同一 folder に空ベース名のファイルが
2件以上あると、自動解決が2件目以降へ ` (1)` を付けてベース名が空でなくなり、除外が解けて
改名要求になる。** これはこのrepositoryが既に文書化・test化している経路である
(`lib/data/rename_exec/occupied_names.dart` の97〜101行、
`test/spec_005_rename_exec/occupied_names_test.dart` の378〜408行)。

つまり 8.0 の実際の振る舞いは「全件が除外」ではなく「**1件目だけ除外、残りは ` (1).ext` へ改名**」で、
**9.0 が止めるのは「利用者が確認していない改名」である。** 承認時の説明より実質が大きいので、
**承認を取り直す。**
