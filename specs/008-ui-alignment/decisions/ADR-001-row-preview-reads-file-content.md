# ADR-001 行のpreviewでfileの中身を読む

- 状態: 採用(2026-08-27、`008:T07`)
- 影響: 002(行の描画)、004(読み込み契約の解釈)、`008:T13`(browserの行)

## 何を決めたか

**一覧の行が、表示のためにfileの中身を読む。** 画像は decode して thumbnail を作り、
動画は platform 側で1frame目を取り出す。取れないものは種別アイコンへ落ちる。

**002 spec へ REQ は足さない。**

## なぜ

`008` は「実機で触って出た、操作の意味が読み取れない」指摘の受け皿である。開発者は
`T07` の着手時に「種別アイコンではなく、スマホのファイルアプリのようなpreviewを出す」
と決めた(`plan.md` の決定表 2026-08-27)。参考designの行データにも `thumbBg` があり、
土台と一致する。

`T07` 以前、appは**fileのmetadataしか読んでいなかった** — 名前、日時、サイズ、そして
folderの実在名(004 REQ-014)である。中身を読むのは新しい。だから「これは仕様の変更か」
を判断する必要があった。

## なぜ REQ を足さないか

002 spec が定めているのは**行が何を表示するか**である。REQ-006/007(変更後名)、
REQ-010(場所)、REQ-013(日時と不明)がそれで、いずれも「行データが何を供給するか」を
言っている。**表示のために何を読むかは定めていない。** そして spec は
「ウィジェットのレイアウト・配色・余白・アイコン・アニメーション(視覚デザインは非規範)」
を対象外に置いている。

読み取りが増えても、次のどれも動かない。

- **改名の判定**: 001 の重複・桁不足・空名・基準日時不明は `FileEntry` の名前と日時だけを
  見る。previewの結果は入らない。
- **読み込み対象**: 004 の決定 D-2「実装が返したものをそのまま扱う」。**種別を推測して
  読み込む file を変えない。** 拡張子の分類は`lib/`の表示専用のもので、`FileSource` へは
  一切戻らない。
- **権限**: 004 が既に取得した範囲の中で読む。新しい権限を要求しない
  (`AndroidManifest.xml` に追加は無い)。

したがって、外部から観測できる**正しさ**は変わらない。変わるのは見え方である。

## 何が新しいriskか

- **時間とメモリ。** 数百件の folder で無制限に読むと遅くなる。`CachedFilePreview` が
  件数上限のLRUと同時実行数の上限を持ち、`ListView.builder` が見えている行しか作らない。
  実機での速度は `T07` の manual 確認が引き受ける。
- **読めない file の見え方。** 「preview が無い」と「読めなかった」を型で分け、行でも
  別のアイコンにする。潰すと、読めない file が普通の file に見える。
- **退避経路。** `013 ADR-002` が保っている Play 却下時の退避では `sourceHandle` が
  SAF の document URI になる。preview は URI を path として開こうとせず「対象外」を返し、
  行は種別アイコンへ落ちる。**退避手順に戻す作業は増えない。**

## 再検討する条件

次のいずれかが起きたら、この判断を見直して 002 へ REQ を足すか、独立した plan にする。

- previewの結果が**改名の判定や読み込み対象へ入る**必要が出たとき(例: 中身から種別を
  決めて絞り込む)。そのときは 004 の D-2 との衝突を先に解く。
- previewのために**新しい権限**が要るようになったとき。
- 「preview が出ること」自体が利用者との約束になり、出ないことを不具合として扱いたく
  なったとき。いまは「あれば出る」ものとして設計している。
