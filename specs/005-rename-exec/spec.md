## 目的（説明的・正誤判定には使わない）

001〜004 で「何に変えるか」は確定し、画面にも出る。005 が**実ファイルを実際に改名する**最後の一歩を担う。あわせて、001 の検証が出している警告(重複・桁不足・空名・基準日時不明)を利用者に見せる責務も持つ。

この機能だけが**取り返しのつかない操作**を行う。ファイル名は利用者の資産で、失敗しても OS 側に Ctrl+Z は無い。そのため、正しさを Strict の契約で固定し、順序・部分失敗・巻き戻しという最も間違えやすい部分を実機なしで網羅的に検証できる形(CON-001)にしている。

## 境界

規範的な境界(in / out)は契約の `scope` が正本。ここには、契約を読むときに必要な**外部の事実**だけを置く。

### 外部依存（ポート）が実際に供給できる値

fake がここに書いた範囲を超えると、その差分の上に乗った要件は本番で無言で死ぬ。値域は記憶で書かず、実機で確かめた事実だけを載せる。

revision 1ではSAFの成功値域から、改名のたびのハンドル更新(REQ-001 / INV-005)と要求名の使用(REQ-018)を導いた。しかしproviderの競合意味論は本物より強いfakeで隠れていた。revision 2ではINV-002を優先し、Android SAF production renameを副作用のない未対応とする。

**revision 4(2026-08-14)で、衝突の扱いが変わった。** 衝突は「改名の失敗」ではなく「001の自動解決が` (n)`で回避するもの」になり、実行時の`nameConflict`は失敗ではなく**再採番して再試行する入口**になった。あわせて衝突判定の「既存の名前」へ**占有名**を用いる — 対象folderの実在名から、そのfolder内で**この実行で改名される選択fileの現在名を除いた**もの。**folderごとに持ち、跨いで混ぜない**(004は複数folderに跨る選択を許すが、改名は同じfolder内で完結する)。読み込んでいないfileとの衝突を拾いつつ、`IMG_0001..0100`を1つずらすような改名が自分たち自身と衝突しないようにするためである(例2・例3)。

**これによりINV-002の成立範囲が環境依存になった。** 原子的no-replaceを提供する環境では完全に成立し、提供しない環境では実在確認と改名の間(TOCTOU)に限り成立しない。**アプリが「上書きしたい」場面を持たなくなったため、no-replaceは破壊を防ぐ最後の砦ではなく、すり抜けた衝突を捕まえて採番へ戻す入口になった。** 判断の全文は[`decisions/ADR-002`](decisions/ADR-002-collision-resolution-by-numbering.md)。Android SAFの未対応(revision 2)は退避経路として維持する。

## 自由とする点（実装に委ねる）

- 実行計画の内部表現、衝突しない順序が複数あるときにどれを選ぶか(OP-001 の `nondeterminism`)。
- 一時名の文字列そのもの(利用者に見えうるので、判別できることだけを要求する)。
- 実行結果・巻き戻し結果の型表現、進捗の刻み方。
- 警告・確認・結果の提示方法(文言・**配置**・UI 部品)。色は `AppColors` のセマンティック色を用いること自体は UI 側の規約。
  **revision 7.0 で一度これを要求へ引き上げたが、revision 8.0 で戻した** — 場所を仕様で書き切ろうとして独立reviewが3回FAILした。REQ-009 が課すのは**利用者から何が読めるか**(種別が一覧の状態で分かる / 変わらない説明を件数ぶん繰り返さない / 全件と説明へ到達できる)であって、配置ではない。

## 対象外・未定義とする点

- 生成後名の決定・警告の判定・自動解決の規則。→ 001-rename-core
- ファイルの読み込み・選択・権限の取得。→ 004-file-source
- ファイルの移動・コピー・削除・内容の変更。意図的に不要(この機能は改名だけを行う)
- セッションを跨いで残る undo 履歴スタック。意図的に不要(単一ステップの巻き戻しのみを扱う)
- Android で更新日時を書き換えること。意図的に不要(SAF に API が無い)
- 巻き戻しで更新日時を元へ戻すこと。巻き戻しは名前だけを戻す(REQ-006)。更新日時ずらしを有効にして実行したあと巻き戻すと、名前は戻るが更新日時はずらした値のまま残る。**意図した受容**(開発者決定 2026-08-12)
- 警告・確認・結果表示の視覚デザイン。→ 008-ui-alignment

### 一時名が残ったときの提示(2026-08-15)

改名portは、目標名に実体があるとき**一時名を経由して**自分自身かどうかを確かめる(`013:T11`)。退避したあとに目標名をもう一度観測し、空いていれば自分自身だったので前進、まだ実在するなら別の実体なので巻き戻す。

**この経路はcase-only改名専用ではない。** 目標名に実体があれば通るので、**ありふれた重複名もここを通る**。しかも再採番(REQ-023)が繰り返されると、**1件の改名要求につき最大`試行上限 + 1`回**この経路を通る。したがって「一時名で出入りする窓」は、当初想定した稀な場面より**広く開く**。この経路には2つの残り方がある。

- **実行中に失敗した場合**: portが元の名前へ巻き戻す(**例外が出た場合も戻す**)。巻き戻しにも失敗したら、**現在の名前(一時名)を理由に含めて返す**。結果の提示(REQ-013)がそのまま利用者へ届ける。**仕組みはある。**
  - このとき実体は一時名にあるので、**`OP-004`の事後条件「失敗時、実体は変化しない」の例外**になる(`open_questions` OQ-007。revision 5で契約へ書く)。
  - **port側の巻き戻し失敗で一時名に残った実体は、`stranded`にも`successes`にも載らない。** これは循環解決の場合に限らず、**すべての衝突経路で起きる**。実行結果は`failure`にしか記録せず、一覧は古い名前を表示し続けるので、**失敗の理由文だけが手掛かりになる**。
  - 循環解決の一時名への改名(REQ-004)がこの経路へ入ると、名前は`<元名>.renaming-N.jpg.renaming-swap-0`のように**二重の一時名**になる。このとき`StrandedFile.currentName`は**計画側の一時名**を報告するので、実体の名前と食い違う(真の現在名は`error.message`に入る)。
  - 巻き戻しに失敗した実体は、`RenameRequest.handle`が元のpathのまま残るので**INV-005も同時に破れる**(`open_questions` OQ-007)。
- **process強制終了・電源断の場合**: **提示する仕組みは無い。** appが動いていないので報告できず、次回起動時に検出する手段も無い(folderを走査する形は`013`のpreflightで失敗した設計である)。**元の名前は空くので次回の実行を妨げない。** 名前(`<元の名前>.renaming-swap-N`)で正体が分かり、利用者が直せる状態にとどまる。**ただし元の名前が長い場合(238 byteを超える場合)は切り詰められる** — 同じ前置を持つ別fileと区別できるよう元名のhashを付けるが、**元の名前そのものは読めない**。hashは`String.hashCode`由来で、**同一buildの範囲でしか一致しない**(言語仕様として実行系・SDK版をまたいだ安定性は保証されない)。

**後者を検出・提示する機能は現時点で対象外**とする。必要になったら別planで扱う(product-mapの将来候補)。
