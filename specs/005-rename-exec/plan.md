## 背景・目的

001〜004 で「何に変えるか」は決まり、画面にも出る。しかし**実ファイルは一度も書き換えていない**。005 がその最後の一歩を担う。

同時に、001 の `validate` が出している警告(重複・桁不足・空名・基準日時不明)は**誰も表示していない**。仕様上は正しいが、利用者から見ると「作成日時トークンを入れたのに何も出ず、理由も分からない」状態で、実質壊れて見える。警告表示は 005 の責務と決めてある(2026-08-02 / 2026-08-05 開発者決定)ので、実行と同じ計画で塞ぐ。

この機能だけが**取り返しのつかない操作**を持つ。ファイル名は利用者の資産で、失敗しても Ctrl+Z は無い。そのため仕様は Strict とし、正しさを契約で固定してから実装する。

## スコープ外

- 永続的な undo 履歴スタック(セッションを跨ぐ巻き戻し)。→ 意図的に不要
- ファイルの移動・コピー・削除。005 は**改名のみ**を行う。→ 意図的に不要
- Android で更新日時を書き換えること(SAF に API が無い)。→ 意図的に不要
- 撮影日時など作成日時の取得経路の追加(001 REQ-010 の範囲)。→ 010-photo-source
- 警告の見た目の作り込み(配色・レイアウト・アニメーション)。→ 008-ui-polish

## 設計方針

- **ポートを1つ増やす**: `RenameExecutor.rename(handle, newName)` → `Renamed(newHandle, name)` / `RenameFailed(reason)`。004 の `FileSource` と同じく、実装は Android(`saf_util.rename`)/ デスクトップ(`File.rename`)/ 未対応 の3つ、テストは fake を注入する(`lib/data/file_source/` の構成を踏襲)。**例外を投げず結果型で返す**のも 004 と同じ。
- **ハンドルは改名のたびに更新する**。T8 の実機スパイクで、SAF は**改名すると URI が変わる**ことが確認されている(ADR-001)。更新しないと連続実行と「元に戻す」が壊れる。戻り値の `name` はドキュメント URI 経由では空だったので、**新しい名前は要求値を使う**。
- **中間状態の衝突を避ける順序で実行する**。001 の `autoResolve` が保証するのは**最終**名集合の一意性だけで、`a→b, b→c` のような入れ替えでは途中で既存ファイルとぶつかる。衝突しない順序に並べ替えて実行し、循環がある場合だけ一時名を1つ挟む。観測可能な要求(既存ファイルを上書きしない)は仕様側で固定する。
- **警告表示は 001 の `Warning` 4種をそのまま流す**(`DuplicateWarning` / `DigitShortageWarning` / `EmptyNameWarning` / `MissingSourceDateWarning`)。005 は判定を持たず、表示と実行可否の制御だけを担う。判定の正本は 001。
- **強制実行 = `autoResolve` の適用**。001 T6 が「強制実行時の名前確定」としてこの関数を用意済みなので、005 は独自の解決規則を作らない。
- 「元に戻す」は**元の URI へ戻すのではなく、新しい URI に対して元の名前で改名し直す**(ADR-001)。実行直前のスナップショット(ハンドル + 元の名前)をセッション内に1件だけ保持する。
